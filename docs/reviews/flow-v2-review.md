## Review

- `skills/orchestrator/salvo/scripts/salvo.py:402-412` - A newly discovered delegate limit is recorded, but the same `salvo.py run` then sleeps until the reset and resumes up to three times. This directly contradicts the new rule that delegate limits never block and work moves to the next `quota pick`: start a previously unmarked candidate that returns a limit resetting in 12 hours, and the lead remains blocked in `sleep_until` for 12 hours instead of receiving the failure and selecting a fallback. Likelihood: high whenever a delegate first hits a limit. Impact: high, because an unattended feature run can stall for most of a day.

- `skills/orchestrator/guard/scripts/guard_lib/rules.py:296-305` - The limit scanner treats any matching prose in an Agent, Task, or SendMessage result as an actual subscription failure, without checking that the tool failed or that the text is a terminal error. For example, an otherwise successful review result containing `a fixture says You've hit your usage limit; try again at 3:05 PM` makes `quota.scan` return a Codex limit and writes it to the machine-wide registry. This is especially reproducible while reviewing the quota code itself. Likelihood: medium. Impact: high, because every session then refuses healthy Codex work until the parsed time.

- `skills/orchestrator/guard/scripts/guard_lib/state.py:76-95` - Archiving a resolved list does not clear its timed hold. Repro: add an item, set a future hold, resolve the item, then add the next task's first item in the same session. `add_items` replaces the list but leaves `hold`; `state.held` therefore exempts the new open item from the stop hook for the old task's remaining wait. Likelihood: medium in long-lived sessions that finish other work before a quota reset. Impact: high, because a later feature can hand back with mandatory work still open.

- `skills/orchestrator/guard/scripts/guard_lib/rules.py:370-388` - Both the rerun and PR-order rules delete all quoted strings before looking for protected commands. A real wrapper such as `bash -lc 'python3 ../verify/scripts/verify.py rerun'` reduces to `bash -lc ` and is allowed while fix delegates run; `bash -lc 'gh pr create ...'` likewise opens before the close step. The same stripping is useful for ignoring quoted log text, but it cannot distinguish a shell program passed to `-c`. Likelihood: medium because shell wrappers are common. Impact: high, because both hard ordering guarantees are bypassed.

- `skills/orchestrator/guard/scripts/guard_lib/rules.py:14,359-361` - A pending todo decision is considered satisfied for the current tool call whenever the raw shell string merely contains `guard.py todo` or `autorun.py start|mode`. Repro: with `todo_undecided` set, run `make deploy; # guard.py todo`; `DECISION.search` succeeds, so the otherwise forbidden command runs although no ledger was created. The state remains undecided, but the guarded work has already happened. Likelihood: low accidentally, but trivial for generated wrapper commands or comments. Impact: high, because the first-tool ledger requirement is not hard.

- `skills/orchestrator/guard/scripts/guard_lib/rules.py:506-517` - The overlong-handback exception is stored forever as only `agent_id -> character count`. After one 301-word handback is blocked and retried, resume the same agent later and submit a different overlong handback with the same character count; it passes on its first attempt because the old count is still present. No delegate-end path clears the entry and content is not compared. Likelihood: low to medium for resumed agents. Impact: medium, because repeated large handbacks permanently inflate the lead context despite the new cap.

- `skills/orchestrator/guard/scripts/guard_lib/verifiers.py:23-41` - The one-verifier budget uses an unlocked read-modify-write of `verifier-rounds.json`. Two concurrent spawn hooks for the same check can both read an empty ledger, both see budget available, and both return success; concurrent spawns for different checks can also overwrite one another's entries. The verification directory is shared across sessions, so the per-session guard state does not serialize this. Likelihood: medium when the flow launches parallel check groups. Impact: high, because the hard separation budget can be exceeded and its evidence ledger corrupted.

- `skills/eng/verify/scripts/verify.py:676-703` - Freeze classification automatically accepts much more than adding checks or Drive contract lines. Changes to an existing check's `Surface`, `Evidence`, `Shape`, title, arbitrary section text, Sensitive paths, or the perf `n/a` reason are put in `edits` or `old_other` and returned as an automatic summary. A direct repro changing only `- Surface: old` to `- Surface: new` returns `([], 'other edits: C1 Surface changed')`, so `freeze` records it without `--revision` or an autonomous user gate. Likelihood: high during ordinary plan refinement. Impact: high, because frozen goalposts and review scope can change without approval.

- `skills/eng/verify/scripts/verify.py:2035-2046` - Premise freshness compares filesystem mtime with the base commit timestamp. A tracked `premises.md` and `grounding.md` written before the base receive current mtimes when cloned, checked out into a new worktree, or restored, so stale premise analysis passes as newly checked against main. The content has no recorded base SHA to close this gap. Likelihood: high when plan artifacts are committed or worktrees are recreated. Impact: high, because implementation can proceed from premises never checked against the adopted base.

- `skills/eng/verify/scripts/verify.py:1042-1056` - Review findings are recognized only on Markdown bullet lines. A section containing `Head: <valid commit>` followed by plain prose such as `Potential auth bypass in app.py:1` produces no problems even though it has neither the required disposition nor `none found`; the same text with a leading `- ` correctly fails. Likelihood: medium because reviewer formatting varies. Impact: high, because real findings can pass the review gate unhandled.

- `skills/eng/verify/scripts/verify.py:1090-1099` - Once the fix-review body contains any finding marked fixed, every later product change is accepted, not just a fix for that finding. The condition rejects a changed product tree only when `FIXED.search(body)` is false. Repro: record one fixed documentation finding, then commit an unrelated auth change after the fix-review Head; `verify.py review` passes without another review. Likelihood: medium in review-fix sequences. Impact: high, because unrelated shipping code can remain outside both reviews.

- `skills/eng/verify/scripts/verify.py:1059-1100` - The gate cannot enforce the specified same-reviewer fix pass. It never reads or requires the top-level `Reviewer:` line and the fix section has no reviewer identity at all, so one agent can write `## Review` and a different agent can append `## Fix review`; valid Head lines and dispositions make the gate pass. Likelihood: medium when the original reviewer cannot be resumed or hits quota. Impact: medium to high, because the intended continuity over the fix diff is silently lost.

- `skills/eng/verify/scripts/verify.py:2073-2077` - The `spec` gate fails open for verification directories created by the previous release. Old `base.json` records contain `base` and `plan` but no `plan_file`, with the copied plan in the verification directory; `plan_file()` deliberately supports that layout, but `cmd_spec` sees the missing `plan_file` and reports that no plan folder was adopted. Thus an in-flight phased feature can skip both its change-log check and `phases` validation. Likelihood: high for exactly the promised backward-compatible existing directories. Impact: high, because the final reconciliation gate is omitted.

- `skills/eng/verify/scripts/verify.py:1430-1476,1517-1531,1777-1799` - Rerun state has no interprocess lock. Two concurrent full `rerun` commands can both read no `scripts.lock.json`, both claim the sole full run, and overwrite the lock; two concurrent `rerun --only` commands load the same ledger and the last `record_runs` write drops the other's check. Logs and fix ledgers have the same class of race. Likelihood: medium because evidence is shared across verifier and lead sessions. Impact: high, because the one-run invariant can be broken and a successful check can disappear from the final report.

- [P1] `skills/eng/verify/scripts/verify.py:1756-1759` - rerun 的例外路徑會保留舊 PASS。修正將 ledger 更新移到 `run_check`，但它只捕捉 `TimeoutExpired`；例如 B1.check.js 曾在同一 HEAD 通過，之後環境找不到 node，`Popen` 拋出 `FileNotFoundError`，外層 `run_checks.work` 雖回報 FAIL，卻不更新 log 或 ledger。針對性 repro 確認兩者寫入次數皆為 0，因此 `report` / `report --write` 仍可接受舊 PASS。發生可能性：中，跨 session 的 PATH、interpreter 或權限差異即可觸發。影響：高，最新失敗被舊的成功證據掩蓋。

- [P2] `skills/eng/verify/scripts/verify.py:2216-2218` - legacy phase 辨識錯把 check ID 字串解包成二元組。`lint_plan()[1]` 回傳字串列表，不是 `(id, line)`；repro：舊 base.json 只有 base/plan，copy 含 B1，兩個 phase 分別含 B1、B2，`adopted_phase` 錯報兩個 owner，因兩者都被截成 B；改用 T5-04 則直接 `ValueError: too many values to unpack`。現有測試只用 B1/C1，掩蓋了錯誤。發生可能性：高，既有 plan 常用相同字首或較長 ID。影響：高，正確的 legacy feature 無法通過最後的 spec gate。

- [P2] `skills/orchestrator/guard/scripts/guard_lib/shell.py:64-78` - 新 parser 不處理 `if` / `while` 等 command-position keyword，讓真正在條件中執行的指令消失。repro：有 running delegate 時，直接 `python3 verify.py rerun --only B1` 被拒，但 `if python3 verify.py rerun --only B1; then :; fi` 的 `order_problem` 回傳 None；`if gh pr create ...; then :; fi` 同樣漏過 PR-order gate。反方向，`decides('if python3 guard.py todo show; then :; fi')` 是 False，合法 todo 決策也會被拒。發生可能性：中，shell 常用條件包住可能失敗的命令。影響：高，可提前 rerun／開 PR，亦可錯擋合法操作。

- [P2] `skills/eng/verify/scripts/verify.py:1919,1939-1948` - 新 lock 仍會把同一次 fix 重複計入 budget。兩個 session 同時 `rerun --only B1`，會在執行前各自保存同一份舊 FAIL ledger；即使兩次都測同一個新 product commit，結尾持鎖時仍各用自己的舊 `before` 呼叫 `fix_attempt`，再分別加 1。以 barrier 強制此交錯的 repro 得到 `{'B1': 2}`，而第一輪結束後順序執行相同測試時 `fix_attempt` 為 False。發生可能性：中，lead/verifier 共用 evidence 時可觸發。影響：高，一次 fix 就耗盡兩次額度，下一次真正修正被跳過。
