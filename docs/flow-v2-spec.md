# Flow v2: implementation spec

Source of truth for the decisions: the design doc "Feature skill redesign" (https://claude.ai/artifact/3nkGAE8bXZKnZ4QqSRLwEy). This file is the concrete contract the implementers build to. Goal of the whole change: save wall-clock time on feature runs while every step is still done, in order, enforced by hard rules. Evidence base: inline-agent phase 5 (863 min wall, about 237 min of work; waste was waiting, e2e reruns invalidated by review fixes, false e2e FAILs, quota waits).

Three workstreams, each owned by one executor, in this worktree (`/Users/justin/cychien/skills-flow-v2`, branch `flow-v2`): A (guard ledger, quota, hooks), B (verify.py), C (skill texts). D (the parlor verify-hello driver) lives in the parlor repo. Names below are contracts between workstreams: build them exactly.

## The new feature flow (what the texts in C describe and A and B enforce)

1. Clarify and basic checks: previous phase merged, base is current main, fresh branch, the project's test suite run once on main; with a plan folder, `verify.py adopt` brings the phase's checks. Gate: `verify.py plan --checks` (checks complete, e2e at most 10; no Drive contract needed yet).
2. How: ground in the code and check every check's premises against main. Artifacts in the plan folder (or the verification directory when there is none): `grounding.md` and `premises.md`. Gate: `verify.py premises`.
3. Design: resolve every false premise, update `spec.md` and later phases (plan folder) or write a short design note, write the Drive contract and Sensitive paths, read the principles index (`../principles/SKILL.md`) and the principles applied, run blast-radius when the design changes a wire format, schema or shared primitive. Gate: `verify.py plan` (full) and `verify.py premises --resolved`.
4. Lock. Gate: `verify.py lock`.
5. Implement (one executor; targeted specs while developing, the whole suite once before hand-back; deviations recorded and reported at hand-back; a "Design decisions" list in the hand-back). Gate: `verify.py units`.
6. E2E scripts, in parallel with step 5 (verifier in its own worktree at base, from plan, skeleton, driver only; attacker actions through driver helpers; every script dry-run on base; a light model compares each script with its plan Scenario). Gate: `verify.py scripts`.
7. Code review, starts when step 5 hands back; findings triaged; fixes proved by unit specs only; then always one fix review by the same reviewer on the fix diff; its fixes proved by unit specs; no e2e here. Gate: `verify.py review`.
8. Prove: one full e2e run on the reviewed code, as parallel as capacity allows, perf scripts alone at the end; `verify.py report --write` builds report.md. Gate: `verify.py oracles`.
9. Fix e2e FAILs: classify each FAIL first (product, script or driver, environment, premise); all fix groups land, then one rerun; no review. Skip when nothing failed.
10. Close and PR: whole unit suite, spec reconciliation, `verify.py report`, `verify.py leftovers`, open-pr. A PR may open with FAIL or INCONCLUSIVE checks; they go at the top of the description and the PR gets the `do not merge` label; merging is the user's gate. Gate: `verify.py report` and `verify.py spec`.

Usage limits never block: delegate work moves to the next candidate (quota, below); only a check that tests one specific agent waits for that agent's quota, which is a timed wait, not a FAIL.

## A. Guard: the ledger, quota, hooks

Evolve guard's todo list into the ledger. Keep the `todo` command family and the state file; add and change:

1. Order. Items copied by `todo from <skill>` get dependencies. Default: an item depends on the previous item from the same `todo from`. A step whose text contains "in parallel with step N", "beside step N" or "in the same message as step N" (case-insensitive, N a number of the same skill) takes step N's dependencies instead, so it opens together with N. Items added with `todo add` have no dependencies and nothing depends on them. `todo done <n>` is refused while a dependency is open or waiting (skipped and done count as resolved), naming the open dependency.
2. Proof of reading. New `todo show <n>`: prints the item's full text, then attachments: for each `../principles/SKILL.md` the item names, the principles skill's body (the index); for each `../principles/references/principles/<x>.md` it names, that file. Last line: `token: <first 6 hex of sha256(text + attachments)>`. `todo done <n>` on an item that came from a skill needs `--token <token>` matching the current text; a wrong or missing token is refused with the command to run. Showing attachments records those principle stems as read.
3. Remove: the rule that an item naming other skills can be done only after those skills were read (and `--not-run`, which existed only for it; accept and ignore the flag for one release with a deprecation line), the "every principle file" rule, and the stop rule on uncited principles (`uncited_principles`). Keep the reply rule, the em dash rule, gates, mandatory, waits, own lists, all other rules.
4. Timed waits. New `todo hold --until <HH:MM or ISO time> --reason "..."`: until that time the stop hook lets the turn end even with open items (a usage limit reset, a long external job). Expires on its own.
5. `todo check`: exits 0 when the list has no open or waiting item, else 1 and the list. Usable as an autorun `--check`.
6. Lint. New `guard.py lint <skill name or SKILL.md path> [--all]`. Reads the skill as `todo from` would. Errors (exit 1): no steps found in a skill whose body mentions "steps"; a parallel phrase names a step number that does not exist; a backticked gate names a script that is not installed beside the skill; a dependency cycle. Warnings (printed, exit 0): a step says "Close this step only when" without a backticked gate; a step is both "Mandatory" and says "Skip this step"; a step names `../<x>/SKILL.md` for a skill that is not installed. `--all` lints every skill under the guard skill roots. Add a test that lints every SKILL.md in this repo with no errors.
7. Hand-back size. On a subagent's stop, when the subagent's final message is longer than 300 words (count CJK characters as half a word each), block once with: put the details in a file and hand back at most 200 words with the file path. A second stop with an unchanged length passes, so a type that cannot write files is not looped.
8. Rerun while delegates run. A shell command that runs `verify.py rerun` (not `--only` either) is denied while the session tracks another running subagent than the caller: "a fix group is still working; rerun once every group has handed back".
9. PR before the close step. `gh pr create` is denied while the lead's list holds an item that names `../open-pr/SKILL.md` and an earlier item from the same skill is unresolved.
10. Quota registry. `~/.agents/orchestrator/limits.json` (override with `ORCHESTRATOR_HOME`), `{ "<agent>": {"until": "<ISO>", "seen": "<ISO>", "source": "<text>"} }`, agent is `claude` or `codex` (the orchestrator config's `agent` values). Expired entries are ignored. Writers: a post-tool rule that scans the result of the Agent and SendMessage tools, and of shell commands that run `codex`, `claude -p` or `salvo.py`, for usage-limit messages: Codex "You've hit your usage limit" with "try again at <time>"; Claude "usage limit" with "reset(s) at <time>" or "resets <time>". Parse the time when present (local time zone; a date in the text wins), else now + 60 min. Never scan other shell output (a log that quotes a limit message must not mark a subscription limited). `salvo.py` also records a limit when a run fails with such a message.
11. Quota pick and spawn checks. `guard.py quota status` prints the registry. `guard.py quota pick --role <planner|executor> [--avoid <agent:model> ...]` prints the first entry of that role in the orchestrator config (project `.agents/orchestrator/models.json`, else `~/.agents/orchestrator/models.json`) whose agent is not limited and that is not avoided, as `agent:model:effort`; exit 1 when every entry is limited ("every candidate is limited until <earliest>; hold until then"). Spawn checks (pre-tool): a shell command that runs `salvo.py run` with an entry, or `codex exec`, whose agent is limited is denied with the `quota pick` result for both roles. A native Agent spawn is not checked (it runs on the lead's own subscription).
12. Reserved subscription. When the branch's verification plan (`verify.py where`, then its plan path) has a check with a line `- Agent: real`, the agents those checks drive other than the lead's own agent are reserved: a `salvo.py run` or `codex exec` on a reserved agent is denied with the `quota pick --avoid` alternative, unless the command is a check script run (`verify.py rerun`). Best effort: when the plan cannot be found, pass.
13. Fallback order, stated in the guard skill text and printed by `quota pick --relax`: first a candidate that keeps every separation rule; then one that relaxes "reviewer from a different family"; then one that relaxes "verifier on a different entry from the executor"; then a candidate from the other role. Each relaxation is reported in the PR's Verification section and in report.md.
14. Tests in `tests/test_guard.py` for every item above, through the existing hook harness, plus a test that runs `todo from feature` on this repo's new feature SKILL.md and asserts the 10 items, their dependencies (6 opens with 5; 7 after 5; 8 after 6 and 7), mandatory flags and gates. Update guard's SKILL.md (rules list, commands) and autorun's SKILL.md (limits: hand the work to `quota pick` instead of waiting; only the lead's own limit or every candidate limited is a wait).

## B. verify.py

1. Remove Touches and `affected`. `plan` no longer asks for Touches (ignore the field if present). `affected` is removed; `rerun --only` stays. The report gate's e2e rule becomes: a PASS needs `<id>.rerun.log` from a passing run after the freeze whose recorded head has no product change before HEAD (product change: any path outside the project's verification skills and the adopted plan folder, the same set `lock` uses).
2. One plan copy. `adopt <phase folder>` records the phase folder's `plan.md` path and the base; every command reads the plan from that path. The verification directory no longer holds a copy. An existing `plan.md` in the verification directory with no adopted path keeps working (back compat).
3. `plan --checks`: the checks part only (fields, tiers, at most 10 e2e, perf decision); no Drive contract required. `plan` (full) adds: a Drive contract when any e2e or walk check exists; names lint: every backticked HTTP path (starts with `/` or `GET|POST|PUT|PATCH|DELETE /`) and every backticked CLI flag (`--name`) in a check's Scenario or Pass must appear in the Drive contract text, else an error naming the check and the name. `phases` no longer requires a Drive contract in phase plans.
4. E2E wording. The cap message and help read: E2E is the most expensive tier, fewer is better, keep only core behavior no unit spec can see, 10 is a ceiling not a target.
5. `premises [--resolved]`: reads `premises.md` beside the plan (plan folder phase directory, else the verification directory). Format: a markdown table with columns `Check | Premise | Holds | Evidence | Resolution`. Passes when every check id of the plan appears in at least one row, every row has Holds `yes` or `no` and non-empty Evidence, and the file is newer than the base commit. `--resolved` also needs a non-empty Resolution on every `no` row. `grounding.md` must exist beside it and be newer than the base commit.
6. Revisions classified. After `lock`, `freeze` with no flag compares the plan with the locked one: when the only changes add checks or add Drive contract lines (no existing check's Scenario, Pass, Tier, Oracle or Seed changed or removed, no contract line removed), it records an automatic revision "additions: <ids and names>" and passes. Any other change needs `--revision "<what and why>"` plus, in an autonomous run, `--gate <id>` of an autorun gate the user answered (read from the autorun run store; refuse otherwise); in an interactive session `--revision` alone. `report` prints every revision.
7. `scripts`: every e2e check has its `<id>.check.<ext>` and a `<id>.base.log` from `verify.py dryrun` showing it reached `verify: ready` and ended with a FAIL line and exit 1 (a predicate failed), not a crash (any other exit, or no ready line, or no FAIL line). New `dryrun [--only <ids>] --base <path to a worktree at the base>`: runs each script with that worktree as its working directory, writes `<id>.base.log`, as parallel as capacity allows. A check whose behavior already exists on base may PASS on base; `scripts` accepts a PASS too and prints it as a note.
8. `review`: `review.md` has a `## Review` with a Head and every finding triaged, and a `## Fix review` section whose Head is HEAD or a commit with HEAD's product tree, every finding triaged. Always required now (the 200-line rule goes).
9. `rerun`: `--jobs` becomes an optional ceiling (default: no ceiling); start the next script whenever `capacity` passes; when it does not, wait (check every 15 s) up to 10 minutes before marking that script REQUEUED and moving on; perf scripts alone at the end, as now. Keep the script lock, `script-fix`, fix budget.
10. `report --write`: builds `report.md` from the evidence (Head, Main, Author and Verifier from flags, one row per check: e2e from the latest `<id>.rerun.log`, unit from `units.json`, walk from `evidence/<id>/`), with each row's Observed cell taken from `observations.md` lines `<id>: <one line>` the verifier writes (subagents cannot write files whose name contains "report"). A FAIL row's cell must start with `defect:`, an INCONCLUSIVE with `blocker:`; missing observations leave the cell `missing` and the gate fails. Plain `report` stays the gate. Add a "Not ready to merge" list at the top of the generated report when any row is FAIL or INCONCLUSIVE.
11. `spec`: in a plan folder, `spec.md` has a `## Change log` section with a line naming this phase (its folder name) or a line `<phase>: no design change`, and `phases` passes. Without a plan folder, passes with a note.
12. Tests in `tests/test_verify.py` for every item; update the help text; remove tests of removed behavior.

## C. Skill texts

Rewrite to the flow above, matching the house style (short declarative sentences, no em dash, no colon mid-sentence). Every gate appears in backticks as `../verify/scripts/verify.py <cmd>` so guard runs it. Steps that cannot be skipped say "Mandatory". Parallel steps say "in parallel with step N".

1. `skills/eng/feature/SKILL.md`: the 10 steps above; remove the throughput checkpoint step and the principles step; step 3 names `../principles/SKILL.md` (so `todo show` attaches the index); keep the owner, keep-the-lead-light, no-blocking rules; the usage-limit fallback and "a PR may open with FAIL" rules; the reply line.
2. `skills/eng/plan-feature/SKILL.md` and `references/phase-plan.md`: write one living `spec.md` in the plan folder (the whole design, skeleton notes folded in, a `## Change log` section) instead of separate design docs and addenda; phase plans hold checks only (no Drive contract, no Sensitive paths, no Touches); the e2e wording; any later phase may edit `spec.md` and later phase plans, logging each change.
3. `skills/eng/verify/SKILL.md` and references (`plan.md`, `plan-template.md`, `verifier-prompt.md`, `reviewer-prompt.md`, `report-template.md`): remove Touches and affected; review before prove; dry-run on base and `verify.py scripts`; script-to-plan comparison by a light model; attacker actions through driver helpers, escalate a safety-classifier refusal at once instead of rewriting around it; FAIL classification; `observations.md` and `report --write`; capacity-driven parallelism; a PR may open with FAIL; e2e wording; premises and grounding.
4. `skills/eng/quick-feature/SKILL.md` and `skills/eng/bug-fix/SKILL.md`: same verification order (review before prove, dry-run, no Touches, report --write).
5. `skills/eng/how/SKILL.md`: when a plan exists, the explorers also check each check's premises; the explainer writes `grounding.md` and `premises.md`; any agent that hands back a file must be a type with a write tool.
6. `skills/eng/open-pr/SKILL.md`: the "Not ready to merge" top section and the `do not merge` label (create it with `gh label create` when missing) when the report has FAIL or INCONCLUSIVE rows.
7. README lines for changed skills.
