# Quick feature

**Cut the ceremony, keep the proof.** A small change still hides the bugs its author cannot see: a month-end date that no mid-month test seeds, a malformed parameter nobody typed. What catches them is a predicate written before the code, seed data shaped at the edges, a drive on the real surface, a verdict from an agent that did not write the change, and a review by one that did not either. This skill keeps all five behind gates, and drops what a small change does not need: design arenas, grounding fan-out, the throughput checkpoint, and review panels.

Paths like `../verify/SKILL.md` point to skills installed beside this one, relative to this file's folder.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from quick-feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why. Pipe command output down to the lines you need, and mark todos in the same call that does the work.

**No blocking, no detours.** In an autonomous run, start it with the `autorun` skill's `--backlog <project backlog>` (such as `docs/backlog.md`), so a reversible question the reviewer cannot settle lands in the backlog with your pick and the run goes on. A bug found on the way that this change does not cause and that no check depends on goes to that backlog with its repro, never into this diff.

**Move to the feature skill** (`../feature/SKILL.md`) the moment any of these holds, and tell the user which one in a line: the change needs more than one PR; it needs a new module, type hierarchy, or state model instead of a copy of a pattern the code already has; it changes a schema, a wire format, a shared primitive, or a flag other code reads; the user has a design question open; or a path a user waits on gains work that scales with data. Add the feature skill's steps with `todo from feature`. The plan and any code carry over, a plan change goes through `verify.py freeze --revision`, and this list's open Mandatory steps close when the same gates pass in the feature run.

1. Scope it and write the plan. Read the code the change touches and name the pattern it copies, a file and a symbol; when there is none, move to the feature skill. List what the request leaves open that the user will see or rely on, and ask it all in one message, because each extra round is idle time. Write the verification plan per `../verify/references/plan.md`: a check per behavior with a literal expected result and a Tier, e2e only where its definition holds, the edges (empty, error, boundary), an oracle check for every value computed from data with seed data shaped to break it (boundary dates, ties, empty groups), a regression check for the flow next to the change, and a perf decision, usually `n/a` with its reason. Lock it before any code exists, so a predicate changed after the code started shows in the report as a revision that names who agreed. Close this step only when `../verify/scripts/verify.py plan` passes and `../verify/scripts/verify.py lock` passes, which refuses once product files have changed. Mandatory: no skip-with-reason escape, because a check written after the code describes the code.
2. Read the **principles** skill (`../principles/SKILL.md`) and the principle files whose entries apply to this change.
3. Get the driver: the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`). Without one, run the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) once in a clean worktree off main, because that one-time cost lets every later change regrade its checks by script, and a driver built after the change learns the change's behavior as the app's. Close this step only when `../verify/scripts/verify.py driver` passes. Mandatory: no skip-with-reason escape.
4. Delegate the code and the scripts in one message. The code goes to one executor from the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`): a native subagent when your agent can run that model, otherwise the **salvo** skill (`../salvo/SKILL.md`) with that one entry. Brief it with the pattern from step 1, the plan's checks as success criteria, a spec written first from the predicates with literal expected values for every unit-tier check, with the check id in its test title, per the Test Behavior, Not Implementation principle (`../principles/references/principles/test-behavior-not-implementation.md`), and comments per the **code-comments** skill (`../code-comments/SKILL.md`), then the **no-comments** skill (`../no-comments/SKILL.md`) on its own diff. It writes no e2e script and commits as it goes, in commits it would keep. The e2e scripts go to the verifier from the **verify** skill's step 5 (`../verify/SKILL.md`), on a different executor-role entry, in its own worktree at the base, from the plan and the driver only. When the plan has oracle checks, start the oracle now as the verify skill's step 4 describes, in the background, so its values exist before the code does. Mandatory: no skip-with-reason escape, because the lead that audits the evidence must not be the change's author.
5. Grade the executor's specs. Close this step only when `../verify/scripts/verify.py units` passes; skip it only when no logic in the change has a cheap local test path, and say so.
6. Prove every check in the plan with the verify skill, sized to the change. Send the same verifier its prove stage: it runs `verify.py rerun` and `verify.py units`, walks each walk-tier check once, and writes `report.md`; you audit every evidence file it names. Fix every FAIL at its root cause and grade the fix with `verify.py rerun --only <ids>` and `verify.py units`, never with a fresh verifier. After 2 failed fix attempts on a check, which `rerun --only` counts and then refuses, stop and take it to the user with its repro, or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL, because a small change that fails twice was not small or its plan was wrong. Close this step only when `../verify/scripts/verify.py oracles` passes. Mandatory: no skip-with-reason escape, because the author's own run is not a verdict.
7. Explore and review, at this change's scale. A fresh explorer from the verify skill's `references/explorer-prompt.md` tries to break the changed flow within the plan's exploration box, 20 minutes unless the plan sets a shorter one, and a fresh reviewer from its `references/reviewer-prompt.md`, on a planner-role model from a different family when the config has one, reviews the diff into `review.md`. Triage every finding per the verify skill's step 11; a new check joins step 6's fix loop with the same budget. Mandatory: no skip-with-reason escape, because the `report` gate refuses a report without them.
8. Final run, then the PR. After the last code change, run `verify.py units` once more, then close this step only when `../verify/scripts/verify.py rerun` passes, `../verify/scripts/verify.py report` passes, and `../verify/scripts/verify.py leftovers` passes. Run the **open-pr** skill (`../open-pr/SKILL.md`) on the commits as they were made, with no regroup and no per-commit runs, because the final run proves the tree that ships. Mandatory: no skip-with-reason escape.

**Reply:** what you built, the pattern it copied, the verify skill's check table, every plan revision, every exploration and review finding with its triage, and any open decision. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`, so quick runs are measured against feature runs.
