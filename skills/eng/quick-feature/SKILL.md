# Quick feature

**Cut the ceremony, keep the proof.** A small change still hides the bugs its author cannot see: a month-end date that no mid-month test seeds, a malformed parameter nobody typed. What catches them is a predicate written before the code, seed data shaped at the edges, a drive on the real surface, a verdict from an agent that did not write the change, and a review by one that did not either. This skill keeps all five behind gates, and drops what a small change does not need: design arenas, grounding fan-out, and review panels.

Paths like `../verify/SKILL.md` point to skills installed beside this one, relative to this file's folder.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from quick-feature` does this and orders the steps: step 4 opens together with step 3, step 5 starts after step 3, and step 6 starts after steps 4 and 5. Print each step with guard's `todo show <n>` before you work it, and close it with the token that prints. Without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why. Pipe command output down to the lines you need, mark todos in the same call that does the work, and ask every subagent for a hand-back of at most 200 words with the details in a file.

**No blocking, no detours.** In an autonomous run, start it with the `autorun` skill's `--backlog <project backlog>` (such as `docs/backlog.md`), so a reversible question the reviewer cannot settle lands in the backlog with your pick and the run goes on. A bug found on the way that this change does not cause and that no check depends on goes to that backlog with its repro, never into this diff. A check that cannot pass in this run stays FAIL or INCONCLUSIVE with its repro, and the PR opens with it, because merging is the user's gate. A usage limit moves a delegate to the next entry `python3 ../guard/scripts/guard.py quota pick --role <planner or executor>` prints, never to a wait.

**Move to the feature skill** (`../feature/SKILL.md`) the moment any of these holds, and tell the user which one in a line: the change needs more than one PR; it needs a new module, type hierarchy, or state model instead of a copy of a pattern the code already has; it changes a schema, a wire format, a shared primitive, or a flag other code reads; the user has a design question open; or a path a user waits on gains work that scales with data. Add the feature skill's steps with `todo from feature`. The plan and any code carry over, a plan change goes through `verify.py freeze`, and this list's open Mandatory steps close when the same gates pass in the feature run.

1. Scope it and decide what verification it needs. Read the code the change touches and name the pattern it copies, a file and a symbol; when there is none, move to the feature skill. Run the project's test suite on main once, so a pre-existing failure is known before the executor meets it. List what the request leaves open that the user will see or rely on, and ask it all in one message, because each extra round is idle time. Write the checks per `../verify/references/plan.md`: a check per behavior with a literal expected result and a Tier, the edges (empty, error, boundary), an oracle check for every value computed from data with seed data shaped to break it (boundary dates, ties, empty groups), a regression check for the flow next to the change, and a perf decision, usually `n/a` with its reason. E2E is the most expensive tier, because every e2e script starts a real instance and runs for minutes, so keep it to core behavior no unit spec can see: fewer is better, zero is fine, and 10 is a ceiling, not a target. Read the code each check relies on, and confirm the check's premise holds there before you rely on it. Mandatory: no skip-with-reason escape, because a check written after the code describes the code.
2. Make the plan concrete and lock it before any code exists. Write its `## Drive contract`, every name the e2e and walk checks drive (test ids and accessible names, routes and HTTP paths, commands and flags, wire and event names, file paths), named the way the copied pattern names its own, and its `## Sensitive paths` (auth, permissions, crypto, and similar) or `n/a` with the reason. Read the principles index (`../principles/SKILL.md`), and read the file of each principle that applies to this change before you cite it. Close this step only when `../verify/scripts/verify.py plan` passes and `../verify/scripts/verify.py lock` passes, which refuses once product files have changed. After the lock, an added check or contract name is recorded on its own, and any other change needs `verify.py freeze --revision` with the user's agreement. Mandatory: no skip-with-reason escape.
3. Implement. The code goes to one executor from the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`): a native subagent when your agent can run that model, otherwise the **salvo** skill (`../salvo/SKILL.md`) with the entry `quota pick --role executor` prints. Spawn it in the same message as the next step's verifier. Brief it with the pattern from step 1, the plan's checks as success criteria, the Drive contract's names to build exactly, a spec written first from the predicates with literal expected values for every unit-tier check, with the check id in its test title, per the Test Behavior, Not Implementation principle (`../principles/references/principles/test-behavior-not-implementation.md`), and comments per the **code-comments** skill (`../code-comments/SKILL.md`), then the **no-comments** skill (`../no-comments/SKILL.md`) on its own diff. It runs only the specs its change touches while it develops and the whole unit suite once before it hands back. A deviation from the pattern or the contract, or a premise it finds false, is written down and reported at hand-back; a name change goes through `verify.py freeze --revision`. It runs no e2e check, neither the verifier's scripts nor the app by hand, writes no e2e script, and commits as it goes, in commits it would keep. Close this step only when `../verify/scripts/verify.py units` passes. Mandatory: no skip-with-reason escape, because the lead that audits the evidence must not be the change's author.
4. Write the e2e scripts, in parallel with step 3. Spawn the verifier from the **verify** skill's step 5 (`../verify/SKILL.md`) on a different executor-role entry (`quota pick --role executor --avoid <the executor's agent:model>`), in its own worktree at the base, strictly from the plan locked at step 2. It first gets the driver, the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`), or creates one in that base worktree with the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`), and commits any driver change alone for you to cherry-pick. It puts every attacker's action in a driver helper, and a safety-classifier refusal comes to you, and from you to the user, at once. It dry-runs every script on the base with `verify.py dryrun`. Then a light model compares each script with its check's Scenario and Pass, and every drift goes back to the verifier. When the plan has oracle checks, start the oracle now as the verify skill's step 4 describes, in the background, so its values exist before the code does. Close this step only when `../verify/scripts/verify.py scripts` passes. Skip this step with the reason only when the plan has no e2e check.
5. Review the code. Starts after step 3. Start a fresh reviewer from the verify skill's `references/reviewer-prompt.md` in Mode `change`, on a planner-role model from a different family when the config has one (`quota pick --role planner --avoid <the executor's agent:model>`), which reviews the diff into `review.md`. Triage every finding per the verify skill's step 6, have the executor fix each `fixed` one at its root cause and prove it with a unit spec, with no e2e run, then send the same reviewer Mode `fix` once and triage that too. Close this step only when `../verify/scripts/verify.py review` passes. Mandatory: no skip-with-reason escape, because review fixes must land before the e2e run so they never void it.
6. Prove, on the reviewed code. Starts after steps 4 and 5. Send the same verifier its prove stage: it runs the change's one full `verify.py rerun`, which runs scripts side by side as far as capacity allows and locks every script (a script that crashed before its predicate is fixed only through `verify.py script-fix` and graded alone with `rerun --only`), and `verify.py units`, walks each walk-tier check once, and writes `observations.md`. Build `report.md` with `python3 ../verify/scripts/verify.py report --write --author <executor agent:model> --verifier <verifier agent:model>`, plus `--note "<text>"` for each quota fallback that relaxed a separation rule, which also goes in the PR's Verification section, and audit every evidence file it names. Close this step only when `../verify/scripts/verify.py oracles` passes. Mandatory: no skip-with-reason escape, because the author's own run is not a verdict.
7. Fix the e2e FAILs. Classify each FAIL per the verify skill's step 11 (product, script or driver, environment, premise) before anyone fixes it. A product defect goes to the executor, a script or driver fault to the same verifier, an environment fault is rerun as it is, and a false premise goes to the user. After every fix has landed, rerun once with `verify.py rerun --only`: every e2e check when a fix changed product code, else only the checks whose scripts changed. Never grade a fix with a fresh verifier, and give these fixes no review. After 2 failed fix attempts on a check, which `rerun --only` counts and then refuses, stop and take it to the user with its repro, or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL, because a small change that fails twice was not small or its plan was wrong. Build the report again with `report --write`. Skip this step with the reason when nothing failed.
8. Close, then the PR. After the last code change, run `verify.py units` once more, and when a product commit landed after the last e2e run, rerun every e2e check once with `verify.py rerun --only`. Close this step only when `../verify/scripts/verify.py report` passes and `../verify/scripts/verify.py leftovers` passes. Run the **open-pr** skill (`../open-pr/SKILL.md`) on the commits as they were made, with no regroup and no per-commit runs, because the closing runs prove the tree that ships. A PR may open with FAIL or INCONCLUSIVE checks, which open-pr lists at the top under the `do not merge` label. Mandatory: no skip-with-reason escape.

**Reply:** what you built, the pattern it copied, the verify skill's check table, every plan revision, every review finding with its triage, and any open decision. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`, so quick runs are measured against feature runs.
