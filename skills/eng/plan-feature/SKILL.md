# Plan feature

**You own the plan, not the code.** The deliverable is a plan folder the feature skill (`../feature/SKILL.md`) builds phase by phase: the decisions, the skeleton, the phases, and a verification plan for each. Write no product code.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from plan-feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`.

The plan folder is the project's design folder for this feature (such as `docs/features/<feature>/`) when the project keeps one, else `<agent store>/plans/<feature>/`. When the folder already holds design docs, start from them instead of redoing settled work.

1. Frame it. State the outcome, who it is for, and the constraints. Read the existing docs, the backlog, and memory for decisions already made, then ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan. Then list every open item the user will see or rely on (inputs, outputs, edges, permissions, failure behavior) and ask them together, because every round is idle time. Settle an item a run can answer with the **prototype** skill (`../prototype/SKILL.md`) instead of asking. Record each decision in the plan's Decisions section.
2. Read the **principles** skill (`../principles/SKILL.md`) and every principle file it indexes. Mandatory: no skip-with-reason escape, because the design and the phase cut both cite them.
3. Ground. Run the **how** skill (`../how/SKILL.md`) over every subsystem the feature touches and save its explanation in the plan folder as `grounding.md`, because the feature skill starts from it instead of exploring again. When the design moves ownership or layering, run the **why** skill (`../why/SKILL.md`) on the current shape. Record external facts the design depends on (a protocol, a platform limit, a library's behavior) in `research.md` with their sources.
4. Design. Run the **architect** skill (`../architect/SKILL.md`) with the grounding and the decisions, and have it save `skeleton.patch` and its rationale in the plan folder. Skip it with the reason when the change only copies patterns the code already has, and write a short design note instead. When the design reaches past its diff (a shared primitive, a wire format, a schema, a flag other code reads), run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the skeleton, fix the design for what it finds, and keep the one safety fact it names for step 6. When the design is contested, run the **interrogate** skill (`../interrogate/SKILL.md`) on it. Take every product decision these surface back to the user, as in step 1.
5. Cut the phases. Write `plan.md` in the plan folder per `references/phase-plan.md`: one phase per PR, each landable and revertible alone, the riskiest unknown first and the verification harness before the features that need it, per the Sequence Work into Verifiable Units principle (`../principles/references/principles/sequence-verifiable-units.md`). Give each phase the skeleton files and symbols it implements and the heavy surfaces it touches, because the feature skill reads those lines to decide what each phase builds and where the expensive checks run.
6. Write every phase's verification plan before any code exists. List the feature's acceptance checks in `plan.md`, then write `phases/<nn>-<name>/plan.md` for each phase per `../verify/references/plan.md`: the checks that phase proves, with expected values, edge-shaped seeds, and an oracle for every computed value; a Tier on every check, `e2e` only for isolation, permissions, revocation, wire compatibility, perf budgets, and cross-surface flows, because each e2e script starts an instance on every rerun, `unit` for logic, and `walk` for UI look and interaction; a check that spans phases goes to the phase where its last piece lands; Regression checks for the earlier phases' load-bearing behavior each phase could break, because no phase reruns another phase's scripts; check ids never repeat across the feature, because the Acceptance list names each check by id; perf where the phase changes a path a user waits on; the blast-radius safety fact as an e2e check in the phase that lands it; and, when a skeleton exists, a conformance check whose `- Skeleton:` field names the files and symbols the phase implements and whose Pass is that the implemented signatures match the skeleton or each difference is in the design addendum with the user's agreement. Present the predicates and budgets to the user in one round, because each is a product decision. Record the folder once with `python3 ../verify/scripts/verify.py phases <plan folder>`. Close this step only when `../verify/scripts/verify.py phases` passes. Mandatory: no skip-with-reason escape, because the feature skill builds and verifies against these plans.
7. Hand back. Give the plan folder, the phases in order with what each proves, and every open decision, then stop. Building starts on the user's go, with the feature skill pointed at the plan folder.

**No blocking, no detours.** In an autonomous run, route a question through the `autorun` skill's `ask` with `--backlog <project backlog>`, so a reversible call the reviewer cannot settle lands in the backlog with your pick and the run goes on. A bug or idea outside this feature goes to the project's backlog (such as `docs/backlog.md`, in its language and format) with where it came from, not into the plan.

**Reply:** the plan folder, the phases with their checks, the decisions made and the ones deferred to the backlog, and what the phases leave unproven. Write it per the **reply** skill (`../reply/SKILL.md`).
