# Plan feature

**You own the plan, not the code.** The deliverable is a plan folder the feature skill (`../feature/SKILL.md`) builds phase by phase: the decisions, one living spec, the skeleton, the phases, and the checks for each. Write no product code.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from plan-feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`.

The plan folder is the project's design folder for this feature (such as `docs/features/<feature>/`) when the project keeps one, else `<agent store>/plans/<feature>/`. When the folder already holds design docs, start from them instead of redoing settled work, and fold them into `spec.md`.

1. Frame it. State the outcome, who it is for, and the constraints. Read the existing docs, the backlog, and memory for decisions already made, then ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan. Then list every open item the user will see or rely on (inputs, outputs, edges, permissions, failure behavior) and ask them together, because every round is idle time. Settle an item a run can answer with the **prototype** skill (`../prototype/SKILL.md`) instead of asking. Record each decision in the plan's Decisions section. Then decide what verification proves the feature: write the Acceptance list in `plan.md` per `references/phase-plan.md`, each check with a scenario, a pass predicate, and a Tier per `../verify/references/plan.md`, an oracle for every value computed from data, and the perf decision. E2E is the most expensive tier, because every e2e script starts a real instance and runs for minutes on every rerun of its phase. Give it only to core behavior no unit spec can see (isolation, permissions, revocation, wire compatibility, perf budgets, and cross-surface flows), give logic `unit` and UI look and interaction `walk`, and treat the cap of 10 per phase as a ceiling, not a target. Name no test id, route, or command yet, because the design settles them. Present the predicates and budgets to the user with the open items, because each is a product decision.
2. Ground. Run the **how** skill (`../how/SKILL.md`) over every subsystem the feature touches and save its explanation in the plan folder as `grounding.md`, because the feature skill starts from it instead of exploring again. When the design moves ownership or layering, run the **why** skill (`../why/SKILL.md`) on the current shape. Record external facts the design depends on (a protocol, a platform limit, a library's behavior) in `research.md` with their sources.
3. Design. Run the **architect** skill (`../architect/SKILL.md`) with the grounding and the decisions, and have it save `skeleton.patch` and its rationale in the plan folder. Skip it with the reason when the change only copies patterns the code already has. Write the whole design into one `spec.md` in the plan folder per `references/phase-plan.md`, with the skeleton's notes folded in and a `## Change log` section, because a design spread over several documents goes stale in some of them and a later phase builds from the stale one. Read the principles index (`../principles/SKILL.md`), pick the principles the design applies, and read each one's file before you cite it. When the design reaches past its diff (a shared primitive, a wire format, a schema, a flag other code reads), run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the skeleton, fix the design for what it finds, and keep the one safety fact it names for step 5. When the design is contested, run the **interrogate** skill (`../interrogate/SKILL.md`) on it. The spec names what the design builds (routes, HTTP paths, commands and flags, test ids and accessible names, wire and event names, file paths), and each phase's feature run writes its Drive contract from it then, because names move with the design and the last moment before code knows them best. Take every product decision these surface back to the user, as in step 1.
4. Cut the phases. Write the Phases section of `plan.md` per `references/phase-plan.md`: one phase per PR, each landable and revertible alone, the riskiest unknown first and the verification harness before the features that need it, per the Sequence Work into Verifiable Units principle (`../principles/references/principles/sequence-verifiable-units.md`). Give each phase the skeleton files and symbols it implements and the heavy surfaces it touches, because the feature skill reads those lines to decide what each phase builds and where the expensive checks run. Name the phase that proves each Acceptance check: a check that spans phases goes to the phase where its last piece lands.
5. Write every phase's checks before any code exists, from the Acceptance list and the design. Write `phases/<nn>-<name>/plan.md` for each phase per `../verify/references/plan.md`, with checks and the perf decision only: no Drive contract and no Sensitive paths, because the phase's feature run writes both from the design as it stands then. Each phase plan holds the Acceptance checks that phase proves, with expected values, edge-shaped seeds, and an oracle for every computed value; Regression checks for the earlier phases' load-bearing behavior it could break, because no phase reruns another phase's scripts; check ids that never repeat across the feature, because the Acceptance list names each check by id; perf where the phase changes a path a user waits on; the blast-radius safety fact as a check in the phase that lands it; and, when a skeleton exists, a unit-tier conformance check whose `- Skeleton:` field names the files and symbols the phase implements and whose Pass is that the skeleton's type tests pass unchanged against the implementation and its import guards hold. Keep e2e checks to what a unit spec cannot see, fewer is better, and never more than 10 per phase: rank them by risk, keep the riskiest and costliest-to-break behavior, and move the rest to `unit`, drop them, or split the phase. Present any predicate or budget added here to the user in one round. Record the folder once with `python3 ../verify/scripts/verify.py phases <plan folder>`. Close this step only when `../verify/scripts/verify.py phases` passes. Mandatory: no skip-with-reason escape, because the feature skill builds and verifies against these plans, and its lock covers each one as written here.
6. Hand back. Give the plan folder, the phases in order with what each proves, and every open decision, then stop. Building starts on the user's go: with the feature skill, one phase per session, pointed at the plan folder and the phase; or, when the user wants speed over per-phase verification, with the **quick-feature** skill (`../quick-feature/SKILL.md`), which builds every phase in one session.

**The spec lives on.** Any later phase may change `spec.md` and the plans of the phases after it, because building shows what planning could not. Each change adds a line to the Change log naming the phase, what changed, why, and which phases it affects, so a reader never has to diff the spec to learn what moved.

**No blocking, no detours.** In an autonomous run, route a question through the `autorun` skill's `ask` with `--backlog <project backlog>`, so a reversible call the reviewer cannot settle lands in the backlog with your pick and the run goes on. A bug or idea outside this feature goes to the project's backlog (such as `docs/backlog.md`, in its language and format) with where it came from, not into the plan.

**Reply:** the plan folder, the phases with their checks, the decisions made and the ones deferred to the backlog, and what the phases leave unproven. Write it per the **reply** skill (`../reply/SKILL.md`).
