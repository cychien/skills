# Plan feature

**You own the plan, not the code.** The deliverable is a plan folder the feature skill (`../feature/SKILL.md`) builds phase by phase: the decisions, what proves the feature, one living spec, the skeleton, and the phases. Write no product code.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from plan-feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`.

The plan folder is the project's design folder for this feature (such as `docs/features/<feature>/`) when the project keeps one, else `<agent store>/plans/<feature>/`. It holds `plan.md`, `spec.md`, and, when the design has one, `skeleton.patch` with its rationale, per `references/plan-folder.md`. When the folder already holds design docs, start from them instead of redoing settled work, and fold them into `spec.md`.

1. Frame it. State the outcome, who it is for, and the constraints. Read the existing docs, the backlog, and memory for decisions already made, then ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan. Then list every open item the user will see or rely on (inputs, outputs, edges, permissions, failure behavior) and ask them together, because every round is idle time. Record each decision in the plan's Decisions section. Then write the Acceptance list in `plan.md`: each item one line in user terms, with what proves it (a unit spec, a drive on the real surface, an oracle over seeds shaped at the edges for a value computed from data, or a perf budget for a path a user waits on). Present the predicates and budgets with the open items, because each is a product decision. Name no test id, route, or command, because the build settles them.
2. Settle the riskiest unknowns. Run the **how** skill (`../how/SKILL.md`) over every subsystem the feature touches, to design from the code as it is. When the design moves ownership or layering, run the **why** skill (`../why/SKILL.md`) on the current shape. Record external facts the design rests on (a protocol, a platform limit, a library's behavior) in `research.md` with their sources. Settle each unknown a run can answer with the **prototype** skill (`../prototype/SKILL.md`) now (a platform behavior, a packaging or install step, a latency the design needs), because a false premise found while planning costs a line and one found mid-build costs a phase.
3. Design. Run the **architect** skill (`../architect/SKILL.md`) with the decisions and what step 2 found, and have it save `skeleton.patch` and its rationale in the plan folder, because the build applies the skeleton instead of writing that code again. Skip it with the reason when the change only copies patterns the code already has. Write the whole design into one `spec.md` per `references/plan-folder.md`, with the skeleton's notes folded in and a `## Change log` section, because a design spread over several documents goes stale in some of them. Read the principles index (`../principles/SKILL.md`), pick the principles the design applies, and read each one's file before you cite it. When the design reaches past its diff (a shared primitive, a wire format, a schema, a flag other code reads), run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the skeleton, fix the design for what it finds, and add its safety fact to the Acceptance list. When the design is contested, run the **interrogate** skill (`../interrogate/SKILL.md`) on it. Take every product decision these surface back to the user, as in step 1.
4. Cut the phases. Write the Phases section of `plan.md` per `references/plan-folder.md`: one phase per PR, each landable and revertible alone, the riskiest unknown first and the verification harness before the features that need it, per the Sequence Work into Verifiable Units principle (`../principles/references/principles/sequence-verifiable-units.md`). Treat a decision only use can settle (how a flow feels, how many prompts it asks) as a risk too: put the phase that makes it usable early, so the user tries it before later phases build on it. Give each phase the skeleton files and symbols it implements, the Acceptance items it proves (an item that spans phases goes to the phase where its last piece lands), and the heavy surfaces it touches.
5. Hand back. Give the plan folder, the phases in order with what each proves, and every open decision, then stop. Building starts on the user's go: with the feature skill, which builds every phase in one session with a cross-family review per phase; or, when the user wants speed over review, with the **quick-feature** skill (`../quick-feature/SKILL.md`).

**The spec lives on.** A later phase may change `spec.md` and the phase entries after it, because building shows what planning could not. Each design change adds a line to the Change log naming the phase, what changed, why, and which phases it affects, so a reader never has to diff the spec to learn what moved. Implementation detail stays out of it.

**No blocking, no detours.** In an autonomous run, route a question through the `autorun` skill's `ask` with `--backlog <project backlog>`, so a reversible call the reviewer cannot settle lands in the backlog with your pick and the run goes on. A bug or idea outside this feature goes to the project's backlog (such as `docs/backlog.md`, in its language and format) with where it came from, not into the plan.

**Reply:** the plan folder, the phases with what each proves, the decisions made and the ones deferred to the backlog, the unknowns settled and how, and what the plan leaves unproven. Write it per the **reply** skill (`../reply/SKILL.md`).
