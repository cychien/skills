# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`), or any project-local verification skill with a feature map. The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live.

Paths like `../open-pr/SKILL.md` point to skills installed beside this one, relative to this file's folder.

## Outcomes

End in exactly one, and say which:

- **clean.** Every feature got source and live coverage, and nothing needs shipping. No branch, no PR.
- **changed.** One PR ships proven doc, harness, or map corrections.
- **blocked.** Coverage could not finish, or a proven fix could not ship safely. Name the blocker.

## Edit scope

Edit only the verification skill's own directory: its `SKILL.md`, `features/`, and any harness scripts it owns. Never edit product code during a run. A behavior the map describes that the app no longer has is either doc drift (fix the map) or a product regression (report it, and do not paper over it in docs).

## Steps

1. **Locate the target.** Find the project-local skill whose body has Launch and Drive sections and a feature map, usually `.agents/skills/verify-*/` or `.claude/skills/verify-*/`. With several candidates, ask which one. With none, stop and point at the **create-verification-skill** skill instead of inventing a target.
2. **Index hygiene.** Read the feature map README and list its sibling files. Fix missing, extra, duplicate, or dead entries.
3. **Source wave.** Launch one read-only subagent per feature file, concurrently, on the executor role of the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`). Each explains how its user-facing feature works from source, flags likely doc drift with `file:line` citations, and returns one concise live-verification recipe. Subagents never drive the app and never edit files. Return shape: feature summary, source entry points, likely drift or none, one recipe.
4. **Reconcile.** Confirm every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift, and do not re-prove clean claims. Sweep recent commits for user-facing surfaces missing from the map, and require a concrete source path before calling one missing. Write a missing feature's expected results from what its PR promised (its description and the spec it cites), not from the implementation, so a shipped bug does not become the map's definition of correct.
5. **Live pass.** Required even when source looks clean. You own all driving. Follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. Load every dataset in the skill's Seed section at least once, and fix any that no longer loads. Exercise every feature at least once, and hold three invariants whatever fails:
   - Never drive an instance you have not health-checked since it last did something surprising. Run doctor before the first drive, on each fresh session, and after any failed drive. Where doctor cannot see the failure (a wedged UI on a healthy process), reset to a known state or relaunch.
   - Evidence captured so far survives every cleanup. Check it at its named location instead of assuming.
   - Nothing a drive started outlives its usefulness. Clean failed-attempt residue whether the session is stuck, exited, or shared. For a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift: fix it under the edit scope and retry once, restarting only what the fix invalidated, before calling the pass blocked. A feature counts as `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted. If the map omits that prerequisite, that is drift. Re-drive every harness fix live before it ships. Tear down after the last drive, re-proofs included.
6. **Triage.** A wrong or missing user-POV description is doc drift: fix it. Working behavior the harness cannot drive is a harness gap: fix it, with scripts executable and their invocation in the skill body. App behavior that is broken is a product gap: record it for the user and keep it out of this PR.
7. **Ship or stop.** For changed, re-read every changed file, then open one PR with the **open-pr** skill (`../open-pr/SKILL.md`). For clean or blocked, open no PR.

Keep run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location, not in the repo.

## Output

Report the outcome, the features covered from source and live, every `verified-unreachable` feature with its prerequisite, the drift fixed, every product gap found, and the PR link when the outcome is changed.
