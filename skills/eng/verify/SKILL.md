# Verify

**You own the verdict, not the driving or the fixing.** A fresh agent that did not write the change drives it and captures evidence. You audit the evidence and decide. This skill never changes product code. An author checks what it meant to build, so its own run is not a verdict.

Paths like `../salvo/SKILL.md` point to skills installed beside this one, relative to this file's folder. Everything this skill writes lives in the verification directory that `python3 scripts/verify.py where` prints, outside the diff; with a plan folder, the plan and its `premises.md` and `grounding.md` stay in the phase's folder, which `verify.py adopt` records. A step that names `../verify/scripts/verify.py <command>` closes only when that command passes; the `guard` skill runs it when you mark the step done, and without guard you run it yourself.

The order is the one a team of engineers keeps. The scripts are written from the plan while the code is written, the review lands its fixes before any e2e run, and the one full e2e run grades the reviewed code, so a review fix never voids an e2e verdict.

1. Get the verification plan: the `plan.md` the calling playbook wrote, or one you write per `references/plan.md`, with a Tier on every check (`e2e`, `unit`, or `walk`); a `## Drive contract` naming everything the e2e and walk checks drive; and `## Sensitive paths`, where a defect costs most and the reviewer looks hardest. E2E is the most expensive tier, because every e2e script starts a real instance and runs for minutes on every rerun, so keep it to core behavior no unit spec can see. Fewer is better, and 10 is a ceiling, not a target. When the calling playbook tested the checks' premises, its `premises.md` gives every false premise a Resolution before this step. Close this step only when `../verify/scripts/verify.py plan` passes, because a vague check gets graded by mood, a missing perf decision means nobody measures, and a script written against names nobody settled tests what the author happened to call things. Mandatory: no skip-with-reason escape.
2. Find the driver. Use the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`) when one exists. Otherwise the verifier runs the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) in step 5, in its own worktree at the base, never in the worktree that holds the change, because a driver built from changed code learns the change's behavior as the app's. Drive the surface directly only for a repo you will not touch again: chrome-devtools-axi for a web UI, a tmux session for a CLI or TUI, curl for an HTTP service.
3. Rebase onto current main, record the head and base SHAs, and freeze the plan. Close this step only when `../verify/scripts/verify.py freeze` passes. Every regression and perf check compares head against this base, and the report gate rejects evidence older than the freeze. After the freeze, `freeze` records an added check or an added Drive contract name on its own, and any other plan change needs a recorded revision per the Fixed goalposts rule. Mandatory: no skip-with-reason escape.
4. Seed and start the oracles. Make sure every Seed the plan names exists as a dataset in the project's verification skill, and add any that is missing: a declarative fixture (JSON, CSV, or SQL) loaded straight into storage, never through the app's business logic, because data made by the code under test inherits its bugs. Copy the seed files into a fresh directory outside the repository, and from there start the oracle with `references/oracle-prompt.md` through the **salvo** skill (`../salvo/SKILL.md`), in the background, on a planner-role model from a different family than the author's when the config has one. Pick it with `python3 ../guard/scripts/guard.py quota pick --role planner --avoid <author's agent:model>`, so a usage limit moves it to the next entry instead of making it wait. Use salvo, not a native subagent, because a native subagent shares your working directory and can read the code it must not see. The oracle writes its values in its own workspace, so it never sees an observation.
5. Write the e2e scripts and dry-run them on the base. Spawn the verifier while the oracle works, and while the code is written when the calling playbook runs them in parallel: a fresh subagent on the executor role of the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`), on a different entry from the one that writes the code when the role has more than one (`quota pick --role executor --avoid <the code writer's agent:model>`). Use a native subagent when your agent can run that model, otherwise the salvo skill with that one entry. Fill `references/verifier-prompt.md` with Stage `scripts`, in its own worktree at the base, and give it the plan, the skeleton, and the driver, nothing about how the code works or why it should pass, because a verifier briefed by the author inherits the author's blind spots. It saves one zero-argument `<id>.check.<ext>` per e2e check, perf checks included, driving only the names in the plan's Drive contract. A name a check needs that the contract lacks comes back to you, and you settle it with the user and record it with `verify.py freeze` instead of letting the verifier guess, because a guessed name tests the guess. An attacker's action (a forged request, a swapped key, a replayed message) goes through a driver helper, and the verifier adds one when the driver lacks it. When a safety classifier refuses that work, the verifier stops and reports it, and you take it to the user at once instead of having the script rewritten around the refusal, because a rewritten script no longer tests the plan's attack. It extends the driver when a check needs it, committing the driver change alone in its worktree for you to cherry-pick. It then runs every script on the base with `verify.py dryrun --base <its worktree>`, which saves each `<id>.base.log`: a check of behavior the base lacks reaches `verify: ready` and fails its predicate, and a crash there is a script or driver bug fixed now instead of at prove. Once it hands back, spawn a light model, the cheapest your agent can run, with the plan and the scripts only, to compare each script's steps and assertions with its check's Scenario and Pass, and send each drift it names back to the verifier, because a script that tests something else grades nothing. Name the check ids the verifier grades on the prompt's Checks line, because guard keeps one verifier per check from it; the scripts it writes do not spend that budget. Split a plan with many independent checks across several verifiers, each on its own instance per the driver's isolation rules. Close this step only when `../verify/scripts/verify.py scripts` passes. Skip this step with the reason only when the plan has no e2e check.
6. Review the code once it lands, before the e2e run. Start a fresh reviewer from `references/reviewer-prompt.md` in Mode `change` on a planner-role model from a different family through salvo, run from the worktree, when the config has one, else on a different entry (`quota pick --role planner --avoid <author's agent:model>`). It reviews the diff from the base to the head adversarially, for security, error paths, concurrency, multi-account state, and wire and back compatibility, and writes `review.md` in the verification directory with the Head it read. Triage each finding: reproduce it or follow its reasoning, and end its line with `Triage: fixed`, `follow-up`, `pre-existing`, or `dismissed` and the reason. A finding is `fixed` only when the change caused it and data is wrong, behavior is wrong, or the user is blocked. The calling playbook's executor then fixes it at its root cause, proves the fix with a unit spec, and runs no e2e, because the e2e run comes after the review. Any other (wording, metadata semantics, an edge no user flow reaches) ends in `Triage: follow-up` with the reason and goes to the project's backlog with its repro, so it ships unfixed in the open instead of starting another loop. A defect that also happens on main is pre-existing and goes to the backlog the same way. Dismiss the rest with the reason. Then send the same reviewer Mode `fix` on the diff from the Head it read to the head, once and always, even when nothing was fixed; it appends a `## Fix review` section, and you triage it the same way. A fix one of its findings needs is proved by its unit spec, with no further review round. Close this step only when `../verify/scripts/verify.py review` passes. Mandatory: no skip-with-reason escape, because review reads paths no check drives.
7. Prove, on the reviewed code. Send the same verifier Stage `prove`, by resuming it or by spawning it again from the prompt, once the scripts and the review are done. It runs the change's one full `python3 scripts/verify.py rerun` and `python3 scripts/verify.py units`, walks every walk check once on the real app with a screenshot or video in `evidence/<id>/`, and writes one line per check to `observations.md`: `<id>: <what it observed>`, a FAIL starting with `defect:` and the repro, an INCONCLUSIVE with `blocker:` and what stopped it. A unit test is the evidence for a unit check, and `units` records which spec proves it. `rerun` runs scripts side by side as far as capacity allows. It starts the next script whenever `verify.py capacity` passes and the running ones printed `verify: ready`, waits up to 10 minutes for capacity before it marks a script REQUEUED, and runs the perf scripts alone at the end, because concurrent instances skew every timing. A REQUEUED script is neither a FAIL nor a fix attempt; grade it with `rerun --only` once the machine is free. The full rerun locks every script and helper: `verify.py` then refuses a second full rerun (only `--full-reason`, which the report prints, overrides it) and any run of an edited file until `verify.py script-fix <file> --reason` records why. Once the verifier hands back, build `report.md` from the evidence with `python3 scripts/verify.py report --write`, naming the author and the verifier, because a subagent cannot write a file named report.
8. Collect the expected values. Once the verifier is done, copy each `<id>.expected.json` from the oracle's workspace into the verification directory; a value that arrives only after the observation was written cannot have shaped it. Close this step only when `../verify/scripts/verify.py oracles` passes. Mandatory: no skip-with-reason escape, because a value checked only by people who saw the code is checked against their expectations. An open question from an oracle is a product decision for the user; settle it, record it with `verify.py freeze --revision`, and compute again.
9. Audit the receipts. Open every evidence file the report names and check it against the predicate yourself. A claim with no evidence file is INCONCLUSIVE whatever the verifier said. Read `scripts.lock.json` for every script fix and full-rerun reason, and refuse any that moved what a script asserts away from its check's Pass, because a weakened assertion turns a FAIL into a PASS with no product change. Do not rerun the scripts yourself: the lock means each log came from the script the plan was graded with.
10. Vet every number with the **benchmark-checklist** skill (`../benchmark-checklist/SKILL.md`) before it counts toward a verdict.
11. Fix the e2e FAILs. Classify every FAIL before anyone fixes it, by reading its `<id>.rerun.log` beside the same script's `<id>.base.log`:
    - **Product**: the app does the wrong thing. Start its Observed line with `defect:` and the repro, and leave the fix to the calling playbook's executor, because the agent that judges a change is never the one that fixes it.
    - **Script or driver**: the script or a driver helper broke or drifted from the plan. It goes back to the same verifier, resumed, which fixes it through `verify.py script-fix` and never moves what the script asserts away from its check's Pass.
    - **Environment**: load, a shared resource another script held (a dialog, a port), or a usage limit. Rerun it as it is; it is not a fix attempt.
    - **Premise**: the check assumes something the product never does. It goes to the user as a predicate change, never a fix attempt.

    Group the fixes by root cause and let every group hand back before anything reruns, because a rerun started while a fix is still landing is wasted; guard denies it. Then rerun once with `python3 scripts/verify.py rerun --only <ids>`: every e2e check when a fix changed product code, because a product change voids every e2e PASS before it, else only the checks whose scripts changed. A fixed walk check goes back to the same verifier, never to a fresh one, because a saved script grades a fix without an agent. These fixes get no further review. Once `report.md` marks a check FAIL, `rerun --only` counts each run in which it still fails, and after 2 failed fix attempts it refuses the check: take it to the user with its repro, what each fix changed, and the premise the fixes shared, per the Attack the Premise principle (`../principles/references/principles/attack-the-premise.md`), or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL. The verifier updates `observations.md`, and you build the report again with `report --write`. Skip this step with the reason when nothing failed.
12. Close every check as PASS, FAIL, or INCONCLUSIVE. Run `python3 scripts/verify.py compare` for the oracle checks. For a mismatch, decide from the spec whether the code, the oracle, or the spec is wrong: a code defect is a FAIL, an oracle misreading gets a fresh oracle, and an ambiguous spec goes to the user. Never edit an expected or observed value by hand. Close this step only when `../verify/scripts/verify.py report` passes and `../verify/scripts/verify.py leftovers` passes: every check has a row, a PASS carries its tier's evidence (an e2e check its script and a passing `<id>.rerun.log` from a run after the freeze with no product change after it, a unit check a passing `units` run on HEAD's tree whose spec names it, a walk check a screenshot or video in `evidence/<id>/`), the report's Head is the current HEAD or a commit with HEAD's tree, every row has evidence on disk written after the freeze, every oracle check's observed value matches its expected value or the row is not PASS, the Verifier is not the Author, each FAIL or INCONCLUSIVE says why, the review and the fix review are triaged, and the machine-wide sweep finds no process an agent left running, because an agent's "all down" is a claim, not proof. When the sweep lists any, run `python3 scripts/verify.py leftovers --kill` before you close; it spares every process whose command line or environment carries `VERIFY_LEAD=1`, and their children, so make `export VERIFY_LEAD=1` the first line of every watcher script of your own. A FAIL or INCONCLUSIVE row does not hold the change back from a PR: `report --write` lists it under "Not ready to merge", and the open-pr skill puts it at the top of the PR. Mandatory: no skip-with-reason escape.
13. Map a new feature. When the change adds a user-facing feature and the project has a verification skill, add the feature's entry to its feature map in this change: entry points and drive steps from what the verifier did, expected results from the plan's predicates, never from reading the implementation.

## Rules

- **Evidence.** Drive the real user path, not internal setters, test-only endpoints, or mocks of your own code. Capture the action and the resulting state, not only the final screen. Read back side effects (a file written, a row inserted, a request sent) alongside what is visible. Mock only where a production boundary already isolates an external system. When the safe path is a dry run or test mode, observe what it skips instead of trusting its name.
- **Not a pass.** A check on the wrong surface, a check that could not run, a unit test standing in for an e2e or walk check, green CI, and an approving review are not PASS. Report INCONCLUSIVE and name the gap. For a unit check, the fail-first spec `units` grades is the evidence.
- **Plan over map.** The feature map says how to reach and drive a feature. The plan says what counts as correct. When the two disagree, the plan wins and the disagreement goes in the report.
- **Fixed goalposts.** Never weaken a predicate, test, baseline, or journey to make it pass, never edit the harness during a run, and never retry a FAIL hoping it passes. Once the plan is frozen, an added check or an added Drive contract name is recorded on its own by `freeze`. Any other change, to an existing check's Scenario, Pass, Tier, Oracle, or Seed or to a contract name, happens only when the user agrees it was wrong: record it with `python3 scripts/verify.py freeze --revision "<what and why>"`, plus `--gate <id>` of the autorun gate the user answered in an autonomous run, and the report prints it. Loosening a perf budget or rule also needs evidence of why it cannot hold, vetted with the benchmark-checklist skill, because the author is the one who wants green. Dropping a check needs the same answer from the user, never only a reviewer's, because a goalpost moved under deadline pressure ships a defect.
- **Fix budget.** One verifier per check; guard denies a second, and the scripts it wrote before the code landed do not spend it. A fix is graded by `verify.py rerun --only` and `verify.py units`, and a fixed walk check by the same verifier, resumed. After 2 failed fix attempts, stop fixing and take the check to the user, or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL. A requeued run and an environment rerun are not attempts.
- **Usage limits.** A delegate that hits a usage limit hands its work to the next entry `guard.py quota pick` prints, instead of waiting for the reset. Only a check that drives one specific agent (`- Agent: real`) waits for that agent's limit, and the wait is not a FAIL.
- **Open is not ship.** A change with FAIL or INCONCLUSIVE checks still gets its PR, with those checks at the top of the description and the `do not merge` label, because the user's merge is the gate, and a run stopped on one check holds every other check back.
- **Pre-existing failures.** A check that also fails on main is a bug the change did not cause. Report it, keep it out of this change's verdict, and keep its fix out of the diff unless the plan covers it.
- **Evidence location.** Keep evidence in the verification directory, named by check id. Cleanup removes instances, never evidence.

## Output

Return the report's table: one row per check with its verdict, evidence path, and one line on what was observed. Above it, name every check the report lists as not ready to merge. Below it, name every plan revision the report gate printed, each regression check's main result, each number with its run count, range, and limiter, every INCONCLUSIVE gap, every pre-existing failure, every check left FAIL after its fix budget, each review finding with its triage, and each quota relaxation. The **open-pr** skill (`../open-pr/SKILL.md`) draws its Verification section from this report and attaches the screenshots and videos that prove a claim.
