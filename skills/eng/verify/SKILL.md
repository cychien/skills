# Verify

**You own the verdict, not the driving or the fixing.** A fresh agent that did not write the change drives it and captures evidence. You audit the evidence and decide. This skill never changes product code. An author checks what it meant to build, so its own run is not a verdict.

Paths like `../salvo/SKILL.md` point to skills installed beside this one, relative to this file's folder. Everything this skill writes lives in the verification directory that `python3 scripts/verify.py where` prints, outside the diff. A step that names `../verify/scripts/verify.py <command>` closes only when that command passes; the `guard` skill runs it when you mark the step done, and without guard you run it yourself.

1. Get the verification plan: the `plan.md` the calling playbook wrote, or one you write per `references/plan.md`, with a Tier on every check: `e2e`, `unit`, or `walk`. Close this step only when `../verify/scripts/verify.py plan` passes, because a vague check gets graded by mood and a missing perf decision means nobody measures. Mandatory: no skip-with-reason escape.
2. Find the driver. Use the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`) when one exists. Otherwise run the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) in a clean worktree off main, never in the worktree that holds the change, because a driver built from changed code learns the change's behavior as the app's. Drive the surface directly only for a repo you will not touch again: chrome-devtools-axi for a web UI, a tmux session for a CLI or TUI, curl for an HTTP service.
3. Rebase onto current main, or for a phase of a stacked feature onto the previous phase's tip, record the head and base SHAs, and freeze the plan. Close this step only when `../verify/scripts/verify.py freeze` passes. Every regression and perf check compares head against this base, and the report gate rejects evidence older than the freeze and any plan edit made after it without a recorded revision. Mandatory: no skip-with-reason escape.
4. Seed and start the oracles. Make sure every Seed the plan names exists as a dataset in the project's verification skill, and add any that is missing: a declarative fixture (JSON, CSV, or SQL) loaded straight into storage, never through the app's business logic, because data made by the code under test inherits its bugs. Copy the seed files into a fresh directory outside the repository, and from there start the oracle with `references/oracle-prompt.md` through the **salvo** skill (`../salvo/SKILL.md`), in the background, on a planner-role model from a different family than the author's when the config has one. If that model cannot run (an outage, a usage limit), move to the next planner entry at once instead of waiting for it. Use salvo, not a native subagent, because a native subagent shares your working directory and can read the code it must not see. The oracle writes its values in its own workspace, so it never sees an observation.
5. Write the e2e scripts. Spawn the verifier while the oracle works, and while the code is written when the calling playbook runs them in parallel: a fresh subagent on the executor role of the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`), on a different entry from the one that writes the code when the role has more than one. Use a native subagent when your agent can run that model, otherwise the salvo skill with that one entry. Fill `references/verifier-prompt.md` with Stage `scripts`, in its own worktree at the base, and give it the plan, the skeleton, and the driver, nothing about how the code works or why it should pass, because a verifier briefed by the author inherits the author's blind spots. It saves one zero-argument `<id>.check.<ext>` per e2e check, perf checks included, and extends the driver when a check needs it. Name the check ids it grades on the prompt's Checks line, because guard keeps one verifier per check from it; the scripts it writes do not spend that budget. Split a plan with many independent checks across several verifiers, each on its own instance per the driver's isolation rules.
6. Prove, once the code lands. Send the same verifier Stage `prove`, by resuming it or by spawning it again from the prompt: it runs `python3 scripts/verify.py rerun` and `python3 scripts/verify.py units`, walks every walk check once on the real app with a screenshot or video in `evidence/<id>/`, and writes `report.md` from `references/report-template.md`. A unit test is the evidence for a unit check, and `units` records which spec proves it, so the verifier grades it from that record. Run the perf scripts alone after the others finish, because concurrent instances skew every timing; `rerun --jobs <n>` runs up to n scripts side by side while `verify.py capacity` would pass, then the perf scripts alone, so pass the number of instances the driver can run at once.
7. Collect the expected values. Once the verifier is done, copy each `<id>.expected.json` from the oracle's workspace into the verification directory; a value that arrives only after the observation was written cannot have shaped it. Close this step only when `../verify/scripts/verify.py oracles` passes. Mandatory: no skip-with-reason escape, because a value checked only by people who saw the code is checked against their expectations. An open question from an oracle is a product decision for the user; settle it, record it with `verify.py freeze --revision`, and compute again.
8. Audit the receipts. Open every evidence file the verifier names and check it against the predicate yourself. A claim with no evidence file is INCONCLUSIVE whatever the verifier said. Re-run the scripted checks with `python3 scripts/verify.py rerun`, because it is cheap and catches a verifier that reported what it expected. A rerun where every script passed leaves a stamp, so a repeat on the same tree, diff, and scripts prints one line instead of running (`--force` runs it anyway), and a script that deletes another check's evidence FAILs.
9. Vet every number with the **benchmark-checklist** skill (`../benchmark-checklist/SKILL.md`) before it counts toward a verdict.
10. Grade every fix by rerun. Never change product code here: start a FAIL's Observed cell with `defect:` and the repro, and leave the fix to the calling playbook's executor, because the agent that judges a change is never the one that fixes it. The executor grades its fix with `python3 scripts/verify.py rerun --only <ids>` and `python3 scripts/verify.py units`, and a fixed walk check goes back to the same verifier, never to a fresh one, because a saved script grades a fix without an agent. Once `report.md` marks a check FAIL, `rerun --only` counts each run in which it still fails, and after 2 failed fix attempts it refuses the check: take it to the user with its repro, what each fix changed, and the premise the fixes shared, per the Attack the Premise principle (`../principles/references/principles/attack-the-premise.md`), or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL, which the full rerun then reports without failing. Skip this step with the reason when nothing failed.
11. Review the code. Start a fresh reviewer from `references/reviewer-prompt.md` on a planner-role model from a different family through salvo, run from the worktree, when the config has one, else on a different entry. It reviews the diff from the base to the head adversarially, for security, error paths, concurrency, multi-account state, and wire and back compatibility, and writes `review.md` in the verification directory. Triage each finding: reproduce it or follow its reasoning, and end its line with `Triage: new check`, `follow-up`, `pre-existing`, or `dismissed` and the reason; the report gate refuses an untriaged finding. A finding becomes a new FAIL check with a tier only when the change caused it and data is wrong, behavior is wrong, or the user is blocked, and it joins step 10 with the same fix budget. Any other (wording, metadata semantics, an edge no user flow reaches) ends in `Triage: follow-up` with the reason and goes to the project's backlog with its repro, so it ships unfixed in the open instead of starting another verify loop. A defect that also happens on main is pre-existing and goes to the backlog the same way. Dismiss the rest with the reason. Close this step only when every finding ends in a triage. Mandatory: no skip-with-reason escape, because review reads paths no check drives, and the report gate refuses a report without a triaged review written after the freeze.
12. Close every check as PASS, FAIL, or INCONCLUSIVE. Run `python3 scripts/verify.py compare` for the oracle checks. For a mismatch, decide from the spec whether the code, the oracle, or the spec is wrong: a code defect is a FAIL, an oracle misreading gets a fresh oracle, and an ambiguous spec goes to the user. Never edit an expected or observed value by hand. Start an INCONCLUSIVE row with `blocker:` and what stopped it. Close this step only when `../verify/scripts/verify.py report` passes and `../verify/scripts/verify.py leftovers` passes: every check has a row, a PASS carries its tier's evidence (an e2e check its script and a passing `<id>.rerun.log` after the freeze, a unit check a passing `units` run on HEAD's tree whose spec names it, a walk check a screenshot or video in `evidence/<id>/`), the report's Head is the current HEAD or a commit with HEAD's tree, every row has evidence on disk written after the freeze, every oracle check's observed value matches its expected value or the row is not PASS, the Verifier is not the Author, each FAIL or INCONCLUSIVE says why, the review is triaged, and the machine-wide sweep finds no process an agent left running, because an agent's "all down" is a claim, not proof. When the sweep lists any, run `python3 scripts/verify.py leftovers --kill` before you close. Mandatory: no skip-with-reason escape.
13. Map a new feature. When the change adds a user-facing feature and the project has a verification skill, add the feature's entry to its feature map in this change: entry points and drive steps from what the verifier did, expected results from the plan's predicates, never from reading the implementation.

## Rules

- **Evidence.** Drive the real user path, not internal setters, test-only endpoints, or mocks of your own code. Capture the action and the resulting state, not only the final screen. Read back side effects (a file written, a row inserted, a request sent) alongside what is visible. Mock only where a production boundary already isolates an external system. When the safe path is a dry run or test mode, observe what it skips instead of trusting its name.
- **Not a pass.** A check on the wrong surface, a check that could not run, a unit test standing in for an e2e or walk check, green CI, and an approving review are not PASS. Report INCONCLUSIVE and name the gap. For a unit check, the fail-first spec `units` grades is the evidence.
- **Plan over map.** The feature map says how to reach and drive a feature. The plan says what counts as correct. When the two disagree, the plan wins and the disagreement goes in the report.
- **Fixed goalposts.** Never weaken a predicate, test, baseline, or journey to make it pass, and never edit the harness during a run. Once the plan is frozen, a check changes only when the user agrees it was wrong; record the change with `python3 scripts/verify.py freeze --revision "<what and why; agreed by whom>"`, which the report gate then prints. Loosening a perf budget or rule also needs evidence of why it cannot hold, vetted with the benchmark-checklist skill, and a countersign from someone other than the author, because the author is the one who wants green: the user, or in an autorun run an `irreversible` gate, which always goes to the user. Shipping a known FAIL or dropping a check needs the same answer, never only a reviewer's, because a goalpost moved under deadline pressure ships a defect.
- **Fix budget.** One verifier per check; guard denies a second, and the scripts it wrote before the code landed do not spend it. A fix is graded by `verify.py rerun --only <ids>` and `verify.py units`, and a fixed walk check by the same verifier, resumed. After 2 failed fix attempts, stop fixing and take the check to the user, or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL. A finding triaged as a new check joins the fix loop with the same budget instead of opening a round of its own.
- **Pre-existing failures.** A check that also fails on main is a bug the change did not cause. Report it, keep it out of this change's verdict, and keep its fix out of the diff unless the plan covers it.
- **Evidence location.** Keep evidence in the verification directory, named by check id. Cleanup removes instances, never evidence.

## Output

Return the report's table: one row per check with its verdict, evidence path, and one line on what was observed. Below it, name every plan revision the report gate printed, name each regression check's main result, each number with its run count, range, and limiter, every INCONCLUSIVE gap, every pre-existing failure, every check left FAIL after its fix budget, and each review finding with its triage. The **open-pr** skill (`../open-pr/SKILL.md`) draws its Verification section from this report and attaches the screenshots and videos that prove a claim.
