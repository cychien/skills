# Feature

**You own the design. Plan, review, verify.** Delegate implementation. Stay in the lead.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

This is the tier for big work. A change that fits one PR and copies a pattern the code already has belongs to the **quick-feature** skill (`../quick-feature/SKILL.md`), unless the user asked for this one. A feature that spans several PRs or is too vague to build is planned first by the **plan-feature** skill (`../plan-feature/SKILL.md`); point this skill at its plan folder and the phase to build, one phase per session, per `references/phases.md`.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from feature` does this and orders the steps: each opens once the one before it closes, step 6 opens together with step 5, step 7 opens once step 5 closes, and step 8 waits for steps 6 and 7. Print each step with guard's `todo show <n>` before you work it, and close it with the token that prints, so every step is read in full, with the principle files it names, before it closes. Without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why.

**You are the owner.** One phase runs in one session, and you take every step yourself: spawn only the executors, the verifier, the reviewer, and the script checker the steps name, plus the agents the skills you run start on their own (the oracle, how's explorers and explainer), never an owner to hand the rest to. A plan folder with several phases runs one phase per session, each started by the user.

**Keep the lead light.** Every lead turn resends the whole conversation, so the lead's context size multiplies the cost of every call. Ask every subagent for a hand-back of at most 200 words with the details in a file you open only to audit, and give any agent that hands back a file a type with a write tool, because a type without one returns the whole file inline. Pipe command output down to the lines you need, and mark todos in the same call that does the work. After spawning a background agent, end the turn or do other work, because its hand-back arrives on its own; guard denies polling for it.

**Usage limits never block.** Pick the entry for every salvo or codex spawn with `python3 ../guard/scripts/guard.py quota pick --role <planner or executor> --avoid <agent:model it must differ from>`, which skips every subscription whose usage limit has not reset. A delegate that hits a limit hands its task and what it already wrote to the next pick, instead of waiting for the reset. When no candidate keeps every separation rule, `quota pick --relax` gives the order to relax them in: first the reviewer's different family, then the verifier's different entry from the executor, then a model from the other role. Name each relaxation (who replaced whom, for which limit, until when) with `--note` on `verify.py report --write`, in the PR's Verification section, and in the reply. Never put a delegate on an agent that a `- Agent: real` check drives, because the delegate would spend the usage window the check needs; guard denies it. Only a check that tests one specific agent waits for that agent's limit. That wait is timed and is not a FAIL, so the rest of the run goes on, and once only that check is left, hold with guard's `todo hold --until <reset time> --reason "<agent> limit for <id>"` and run it after the reset. Only your own limit, or every candidate limited, stops the run.

**Shared machine.** Instances share one machine, so start them one at a time and only while `verify.py capacity` passes (with `--native` for a native build); `verify.py rerun` does both on its own. When the load exceeds the cores, run `verify.py leftovers --kill` before blaming the busy workers, because orphans from earlier delegates are the usual cause. Make `export VERIFY_LEAD=1` the first line of every watcher script of your own, so the marker sits in its command line, where `leftovers` reads it on macOS, and a delegate's `leftovers --kill` spares it and its children.

**No blocking, no detours.** In an autonomous run, start it with the `autorun` skill's `--backlog <project backlog>` (such as `docs/backlog.md`), so a reversible question the reviewer cannot settle lands in the backlog with your pick and the run goes on with it. A check that cannot pass in this run never holds the run. After its fix budget, or when a safety classifier refuses the step that drives it, it stays FAIL or INCONCLUSIVE with its repro, what was tried, and the next step you recommend, and the PR opens with it, because merging is the user's gate, not opening. A bug or idea found on the way that this feature does not cause and that no check depends on goes to that backlog with its repro and where it came from, never into this diff, because each such fix starts another verify loop. Fix one here only when a check of this feature cannot pass without it, on its own branch cut from main and as its own PR through the **bug-fix** skill (`../bug-fix/SKILL.md`), so nothing has to come off the feature branch later.

1. Clarify the requirements and run the basic checks. Confirm the base: the previous phase is merged and the base is current main, or its PR is still open and this phase stacks on its branch, with the PR opened against that branch. Fetch main, cut a fresh branch and worktree from that base, and run the project's test suite there once. A pre-existing failure goes to exactly one owner, because otherwise every executor meets it and fixes it again. With a plan folder from the plan-feature skill, the decisions and this phase's checks are settled: run `python3 ../verify/scripts/verify.py adopt <plan folder>/phases/<phase>` on the fresh branch, which points the branch at the phase's plan and records its base, and ask only what the plan leaves open. Otherwise review the spec and list what it leaves open that the user will see or rely on: inputs, outputs and their format, behavior at the edges, and scope. Read the spec's status line, the feature docs, and memory for decisions already made, and ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan. Write the checks as `plan.md` in the verification directory that `verify.py where` prints, per `../verify/references/plan.md`: a scenario, a pass predicate, and a Tier on each; the seed data each check needs; an oracle for every value computed from data; and the perf decision, a perf check only for a path where the change adds work the user waits on or work that scales with data. E2E is the most expensive tier, because every e2e script starts a real instance and runs for minutes on every rerun. Keep it to core behavior no unit spec can see. Fewer is better, zero is a fine plan, and 10 is a ceiling, not a target. Name no test id, route, or command yet, because step 3's design settles them. Each open item, predicate, and budget is a product decision, so discuss them with the user in one round before designing. Settle an item a run can answer with the **prototype** skill (`../prototype/SKILL.md`) first. Do not copy the plan's checks into the todo list, because the `report` gate already refuses a check without a verdict. Close this step only when `../verify/scripts/verify.py plan --checks` passes. Mandatory: no skip-with-reason escape, because every later step builds and verifies against these checks.
2. Ground in the code, and test every check's premises against main. Run the **how** skill (`../how/SKILL.md`) over the subsystems the checks run through, and give it the plan and the base commit (the one `verify.py adopt` printed, else the merge-base with main), so its explorers also test each check's premises on current main with a file and line for each, and its explainer writes `grounding.md` and `premises.md` beside the plan, each starting with a `Base: <sha>` line, in the phase's folder with a plan folder and in the verification directory without one. When the plan folder or an earlier phase left a `grounding.md`, hand it to how as the starting model and scope the explorers to what changed since and to the premises. One explorer also lists what the project's driver can and cannot drive on each Surface the checks name, with the command for each, because step 3 writes the Drive contract against it. When a Surface the checks need is one the driver cannot drive, start that driver work now in its own worktree at the base, on an executor-role entry briefed with the plan's Surfaces and Scenarios only, so it runs beside steps 3 to 5 instead of in front of the scripts; step 6's verifier takes the driver from it and still writes the scripts only after the lock. Decide nothing here. A premise that does not hold is a row with Holds `no` and its evidence, and step 3 resolves it, because a choice made while exploring skips the design and the user. Close this step only when `../verify/scripts/verify.py premises` passes, which needs both files to name the base in their `Base:` line and a row for every check, so a premise checked at an older commit never passes for this one. Mandatory: no skip-with-reason escape, because a false premise found here costs a line and one found at prove costs a fix round.
3. Design how it will be built, and settle every name the checks drive. First resolve every `no` row of `premises.md` and write its Resolution: the design adds what is missing, the check changes with the user's agreement, or the check moves to a later phase. Then decide which case holds and write it on the todo item, because the cases cost very different amounts:
   - **A: a plan folder exists.** Update its `spec.md` wherever the grounding, a premise, or this phase's design contradicts it, and update every later phase plan the change affects (scope, checks). Log each change as a line in the spec's `## Change log`: this phase's folder name, what changed, why, and which phases it affects. The skeleton stays the contract for the files it covers.
   - **B: no plan folder, and the change follows existing patterns.** Write a short design note in the verification directory: types, module placement, data flow.
   - **C: no plan folder, and the architecture is novel or cross-cutting.** Run the **architect** skill (`../architect/SKILL.md`), saving `skeleton.patch` and its rationale in the verification directory, and add a unit-tier conformance check to the plan whose `- Skeleton:` field names the files and symbols this change implements and whose Pass is that the skeleton's type tests pass unchanged against the implementation and its import guards hold.

   Then write into the plan its `## Drive contract`, every name the e2e and walk checks drive (DOM test ids and accessible names, routes and HTTP paths, CLI commands and flags, wire and event names, the file paths the checks read). Take a name that exists today with its real value from `grounding.md`, and a new one from the design and the skeleton, because a name written without reading main points at the wrong place. Write its `## Sensitive paths` too, the paths the design touches where a defect costs most (auth, permissions, crypto, and similar), per `../verify/references/plan.md`. Read the principles index (`../principles/SKILL.md`), which `todo show` prints with this step, pick the principles the design applies, and read each one's file before you cite it. Run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the design when it changes a wire format, a schema, a shared primitive, or a flag other code reads, fix the design for what it finds, and add its safety fact to the plan as a check, because a risk found on paper costs a line. When candidates split on a premise a run can check, settle it with the prototype skill. A product decision found here goes back to the user as in step 1. Close this step only when `../verify/scripts/verify.py plan` passes, which refuses an e2e or walk check without a Drive contract, a backticked HTTP path or CLI flag in a check that the contract lacks, and more than 10 e2e checks, and `../verify/scripts/verify.py premises --resolved` passes. Mandatory: no skip-with-reason escape, because the code and the scripts are both built from what this step writes.
4. Lock the plan, its checks with their Drive contract and Sensitive paths, before any code exists. Close this step only when `../verify/scripts/verify.py lock` passes, which refuses once product files have changed. After the lock, `verify.py freeze` records an added check or an added contract name on its own. Any other change to the plan needs `verify.py freeze --revision "<what and why>"`, and in an autonomous run also `--gate <id>` of the autorun gate the user answered, because a predicate edited after the code was seen describes the code. Only this phase's plan is locked: `spec.md` and the later phase plans stay open to change, each change logged in the Change log. Mandatory: no skip-with-reason escape.
5. Implement. Delegate code-writing to one executor on the executor model from the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`): a native subagent when your agent can run that model, otherwise the **salvo** skill (`../salvo/SKILL.md`) with the entry `quota pick --role executor` prints. Use one executor, because each extra agent reads the codebase again and its work must be merged. Spawn it in the same message as the next step's verifier, because the scripts need only the locked plan. Brief it with:
   - The skeleton, when one exists: its first commit applies the skeleton's files for this change, and the skeleton is the contract.
   - The Drive contract: it builds every name there exactly, because the verifier's scripts drive those names.
   - The scope: file paths and the named data shape with its organizing structure, per the Model the Domain principle (`../principles/references/principles/model-the-domain.md`).
   - The success criteria: the plan's checks; a spec written to fail first for every unit-tier check, with the check id in its test title, because `verify.py units` records which spec proves which check; typecheck, lint, and `verify.py units` green before it hands back; comments per the **code-comments** skill (`../code-comments/SKILL.md`), then the **no-comments** skill (`../no-comments/SKILL.md`) on its own diff, because the author removes a comment cheapest. It runs no e2e check, neither the verifier's scripts nor the app by hand, and writes no e2e script, because the verifier grades every e2e check and a script its author writes checks what the author meant to build.
   - The test runs: while it develops, it runs only the specs its change touches, and it runs the project's whole unit suite once before it hands back, because a suite run per edit costs a phase about 20 minutes.
   - The deviations: a difference from the skeleton or the Drive contract (a parameter, a type, a module, or a name the design did not anticipate), and a premise it finds false, are written down where they happen and the work goes on. The hand-back lists each one, with whether the design was wrong, the requirement was missed, or the implementation overreaches. You approve an internal one. A public one, or a Drive contract name, needs the user's agreement, and a name change goes through `verify.py freeze --revision`. Write each approved deviation into `spec.md` or the design note.
   - The design decisions: the hand-back ends with a "Design decisions" list of every choice it made that changes behavior (a timeout, a default, a value on the wire), and you write each one into `spec.md` or the design note, because the executor never edits the spec.

   It commits as the work goes, in commits it would keep, because the history is never regrouped. When the implementation admits several valid shapes, delegate through the **arena** skill (`../arena/SKILL.md`) instead. Run one agent per worktree at a time, stopping the previous agent's task and running `verify.py leftovers --kill` before another touches it. When the same kind of friction keeps coming back (one workaround repeated across unrelated code, special cases for unrelated edges, types that need casts or always-set optionals, a lock the design said was not needed, callers that must know the internals), the design is wrong: stop, rerun the architect skill from what was learned, and subtract before adding, per the Subtract Before You Add principle (`../principles/references/principles/subtract-before-you-add.md`), instead of patching. Close this step only when `../verify/scripts/verify.py units` passes and you approved every deviation the hand-back lists. Mandatory: no skip-with-reason escape, because the gain is review separation, not lines saved.
6. Write the e2e scripts, in parallel with step 5. Spawn the verifier from the **verify** skill's step 5 (`../verify/SKILL.md`) on an executor-role entry other than the code writer's (`quota pick --role executor --avoid <the executor's agent:model>`), in its own worktree at the phase's base, briefed from the plan, the skeleton, and the driver only, because a script written from the code checks the code. It first gets the driver, the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`): the one on main, or a new one from the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) in that base worktree, because a driver built from the change learns the change's behavior as the app's. It commits a driver change alone in its worktree, and you cherry-pick it onto the phase branch. It writes one zero-argument `<id>.check.<ext>` per e2e check, driving only the Drive contract. A name a check needs that the contract lacks comes back to you to settle, never a guess. An attacker's action in a scenario (a forged request, a swapped key) is a driver helper the script calls, and the verifier adds the helper to the driver when it is missing. When a safety classifier refuses that work, the verifier stops and reports the refusal, and you take it to the user at once instead of having the script rewritten around it, because a rewrite drifts from the plan. It dry-runs every script on the base with `verify.py dryrun`, where a check of behavior the base lacks must reach `verify: ready` and fail its predicate, not crash before it. Then spawn a light model, the cheapest your agent can run, to compare each script with its check's Scenario and Pass, and send every drift back to the verifier, because a script that tests something else turns its verdict into noise. Close this step only when `../verify/scripts/verify.py scripts` passes. Skip this step with the reason only when the plan has no e2e check; a walk check then gets the driver at step 8.
7. Review the code. Starts after step 5, without waiting for the scripts. Start a fresh reviewer: a planner-role model from a different family through salvo when the config has one, else a different entry (`quota pick --role planner --avoid <the executor's agent:model>`), briefed with the verify skill's `references/reviewer-prompt.md` in Mode `change`. It reviews the phase diff adversarially for security, error paths, concurrency, multi-account state, and wire and back compatibility, hardest on the Sensitive paths, and writes `review.md` in the verification directory with the Head it read, because it reads paths no check drives. Triage every finding per the verify skill's step 6. Give the findings to fix, grouped by root cause, to fresh executors, each of which proves its fix with a unit spec and runs no e2e, because the one e2e run belongs to step 8, on the reviewed code. A fix that changes behavior goes into `spec.md` or the design note. Then send the same reviewer Mode `fix` on the diff from the Head it read, once and always, even when nothing was fixed. Triage its findings the same way, prove each fix one needs with a unit spec, and stop there with no third round. Once those fixes land, write `Fixed at: <sha>` into the `## Fix review` section, the commit that holds them, or its Head when nothing was fixed, because the gate holds HEAD to that commit's product code. When the same reviewer cannot take the fix review (its quota ran out), take the next candidate from `quota pick --relax` and add `Relaxed: <reason>` to the section, which the report lists. When an implementation choice is contested, also run the **interrogate** skill (`../interrogate/SKILL.md`). Close this step only when `../verify/scripts/verify.py review` passes. Mandatory: no skip-with-reason escape, because review finds what no check drives, and its fixes must land before the e2e run so they never void it.
8. Prove, on the reviewed code. Starts after steps 6 and 7. Send the same verifier its prove stage. It runs the change's one full `verify.py rerun`, which starts each next script whenever `verify.py capacity` passes and runs the perf scripts alone at the end, and `verify.py units`. It walks every walk-tier check once on the real app with a screenshot or video in `evidence/<id>/`, and writes one line per check in `observations.md`. Then build `report.md` with `python3 ../verify/scripts/verify.py report --write` and its flags `--author <agent:model>`, `--verifier <agent:model>`, and one `--note "<text>"` per quota fallback that relaxed a separation rule, with the executor as the author and the verifier as the verifier. That full rerun locks every script, and `verify.py` refuses a second full rerun and any rerun of an edited script without `verify.py script-fix <file> --reason`, which the verifier records only for a script that crashed before its predicate and then grades alone with `rerun --only`. Collect the oracles' values as the verify skill says, and audit every evidence file the report names yourself. Close this step only when `../verify/scripts/verify.py oracles` passes. Mandatory: no skip-with-reason escape, because the author's own run is not a verdict.
9. Fix the e2e FAILs. Classify every FAIL before anyone fixes it, by reading its `<id>.rerun.log` beside the same script's `<id>.base.log`, per the verify skill's step 11. A product defect goes to a fresh executor, which fixes it at the root cause and adds a unit spec wherever one can see it. A script or driver fault goes back to the same verifier, resumed, which fixes it through `verify.py script-fix` and never moves what a script asserts away from its check's Pass. An environment fault (load, a dialog another script answered, a usage limit) is rerun as it is and is not a fix attempt. A false premise goes to the user as a predicate change, never a fix attempt. Spawn the fix groups together, one per root cause. Rerun once, after every group has handed back: `verify.py rerun --only` with every e2e check when a fix changed product code, because a product change voids every e2e PASS before it, else with only the checks whose scripts changed; guard denies a rerun while a group still works. A fixed walk check goes back to the same verifier. These fixes get no review, because the review already ran and what is left is small. Never spend a fresh verifier on a fix, because a saved script grades it without one, and guard allows one verifier per check. A check gets at most 2 failed fix attempts. Once `report.md` marks it FAIL, `verify.py rerun` counts a run in which it still fails as one attempt when a product file or its script changed since its previous failing run, and after 2 every rerun skips it with a note. Take it to the user with its repro, what each fix changed, and the premise the fixes shared, per the Attack the Premise principle (`../principles/references/principles/attack-the-premise.md`), or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL. The verifier updates `observations.md`, and you build the report again with `report --write`. Skip this step with the reason when nothing failed.
10. Close, then the PR. After the last code change, run the project's whole unit suite and `verify.py units` once more, because the report holds each unit check to a units run on the code that ships and a change can break a spec it never touched. When a product commit landed after the last e2e run, rerun every e2e check once more with `verify.py rerun --only`, because the report gate refuses an e2e PASS older than a product change. Reconcile the design with what ships. With a plan folder, `spec.md` describes the shipped behavior, its Change log has a line for this phase (`<phase>: no design change` when there was none), and every later phase plan still passes `verify.py phases`; without one, the design note matches the code. Run `verify.py leftovers --kill` when `verify.py leftovers` lists any process. Close this step only when `../verify/scripts/verify.py report`, `../verify/scripts/verify.py spec` and `../verify/scripts/verify.py leftovers` pass. Run the **open-pr** skill (`../open-pr/SKILL.md`) on the commits as they were made, with no regroup and no per-commit runs, because the closing runs prove the tree that ships; open it against main, or against the previous phase's branch when this phase stacks on it. A PR may open with FAIL or INCONCLUSIVE checks, which open-pr lists at the top of the description under the `do not merge` label. Never merge, because the user lands every PR. Mandatory: no skip-with-reason escape.

Give follow-up work to a fresh executor rather than resuming a long one, because a resumed agent pays its whole context again on every call. Tell the user when the phase ends and what the next session starts: the next phase, on main once this PR merges, or stacked on this branch while it is open.

**Reply:** what you built, what you chose and why, the agents the run used with any quota relaxation, the verify skill's check table, every review finding with its triage, each item added to the backlog, and open decisions. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`, so every run is measured against the last.
