# Feature

**You own the design. Plan, review, verify.** Delegate implementation. Stay in the lead.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

This is the tier for big work. A change that fits one PR and copies a pattern the code already has belongs to the **quick-feature** skill (`../quick-feature/SKILL.md`), unless the user asked for this one. A feature that spans several PRs or is too vague to build is planned first by the **plan-feature** skill (`../plan-feature/SKILL.md`); point this skill at its plan folder and build each phase per `references/phases.md`.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why.

**Keep the lead light.** Every lead turn resends the whole conversation, so the lead's context size multiplies the cost of every call. When this session already carries a finished task, or the lead passes 200k tokens of context at a phase boundary (`../reflect/scripts/profile.py <transcript> --context`), hand the rest to a fresh owner subagent on your own model with a handoff brief, and only relay. Ask every subagent for a hand-back of at most 200 words with the details in a file you open only to audit. Pipe command output down to the lines you need, and mark todos in the same call that does the work. After spawning a background agent, end the turn or do other work, because its hand-back arrives on its own; guard denies polling for it. An owner that is itself a subagent runs its agents in the foreground, several Agent calls in one message for parallel work, because its background children die when its turn ends; guard denies the background spawn.

**No blocking, no detours.** In an autonomous run, start it with the `autorun` skill's `--backlog <project backlog>` (such as `docs/backlog.md`), so a reversible question the reviewer cannot settle lands in the backlog with your pick and the run goes on with it. A bug or idea found on the way that this feature does not cause and that no check depends on goes to that backlog with its repro and where it came from, never into this diff, because each such fix starts another verify loop. Fix one here only when a check of this feature cannot pass without it, as its own PR through the **bug-fix** skill (`../bug-fix/SKILL.md`).

1. Clarify the requirements and what proves them. With a plan folder from the plan-feature skill, the decisions and this phase's plan are settled: run `python3 ../verify/scripts/verify.py adopt <plan folder>/phases/<phase>` on the phase's fresh branch, and ask only what the plan leaves open. Otherwise review the spec and list what it leaves open that the user will see or rely on: inputs, outputs and their format, behavior at the edges, and scope. Read the spec's status line, the feature docs, and memory for decisions already made, and ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan. Draft the verification plan per `../verify/references/plan.md` alongside: perf acceptance, the seed data each check needs, an oracle check for every value computed from data, and a Tier on every check, `e2e` only where its definition holds. Each open item, predicate, and budget is a product decision, so discuss them with the user in one round before designing. Settle an item a run can answer with the **prototype** skill (`../prototype/SKILL.md`) first. A perf check exists only for a path where the change adds work the user waits on or work that scales with data. Do not copy the plan's checks into the todo list, because the `report` gate already refuses a check without a verdict. Close this step only when `../verify/scripts/verify.py plan` passes. Mandatory: no skip-with-reason escape, because every later step builds and verifies against this plan.
2. Read the **principles** skill (`../principles/SKILL.md`) and every principle file it indexes. Mandatory: no skip-with-reason escape, because the principles shape every later step and a citation is only honest when its file was read.
3. Run the **how** skill (`../how/SKILL.md`) over the affected subsystem. When a plan folder or an earlier phase left a grounding document, hand it to how as the starting model and scope the explorers to what changed since; when it already covers every subsystem this change touches, close this step with `--not-run how` and that reason.
4. Settle the design shape. Decide which case holds and write it on the todo item, because the cases cost very different amounts:
   - **A: a design and its skeleton exist and still apply** (a plan folder, or a design doc). Diff them against the step 3 grounding and write a one-page addendum for what current code contradicts and any open decision; skip the addendum when there is none.
   - **B: no design, and the change follows existing patterns.** Write a short design note: types, module placement, data flow.
   - **C: no design, and the architecture is novel or cross-cutting.** Run the **architect** skill (`../architect/SKILL.md`), saving `skeleton.patch` and its rationale in the verification directory, then add a conformance check to the plan whose `- Skeleton:` field names the files and symbols this change implements and whose Pass is that the implemented signatures match the skeleton or each difference is in the addendum with the user's agreement.

   A product decision found here goes back to the user as in step 1. Without a plan folder that already did it, run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the design artifact when the change reaches past its diff (a shared primitive, a wire format, a schema, a flag other code reads), fix the design for what it finds, and add its safety fact to the plan as a check, because a risk found on paper costs a line. When candidates split on a premise a run can check, settle it with the prototype skill.
5. Lock the plan before any code exists. Close this step only when `../verify/scripts/verify.py lock` passes: it refuses once product files have changed, and afterwards every change to a check or budget needs `verify.py freeze --revision` naming who agreed, because a predicate edited after the code was seen describes the code. Mandatory: no skip-with-reason escape.
6. Write the throughput checkpoint as five todo items. A dimension that does not apply keeps its item with `n/a: <reason>`:
   - **Blocking first steps.** Run the project's test suite on main once first, and give any pre-existing failure to exactly one owner, because otherwise every executor meets it and fixes it again.
   - **Independent workstreams.** One executor writes the code, because each extra agent reads the codebase again and its work must be merged. Add a second only when the phase's e2e checks do not span both workstreams, so each half is proved on its own, and say why here.
   - **Agents.** List every agent the run will spawn with its subscription and effort, because they share one usage window: the executor; one verifier and one explorer on a different executor-role entry from the code writer; and one reviewer on a planner-role model from a different family when the config has one, else on a different entry. The verifier, the explorer, and the reviewer never wrote the code, because an author checks what it meant to build.
   - **Shared mutable state.** Default to splitting the target, per the Separate Before Serializing Shared State principle (`../principles/references/principles/separate-before-serializing-shared-state.md`). Serialize only for real invariants.
   - **Machine capacity.** Before every spawn or instance start, run `../verify/scripts/verify.py capacity` (with `--native` for a native build), which passes while the 1-minute load is under 0.7 x cores and no native build runs. Start instances one at a time. Run perf scripts alone after the others, because concurrent instances skew every timing. When the load exceeds the cores, run `../verify/scripts/verify.py leftovers --kill` before blaming the busy workers, because orphans from earlier delegates are the usual cause.
7. Get the driver: the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`). Without one, run the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) in a clean worktree off main, because a driver built after the change learns the change's behavior as the app's. Close this step only when `../verify/scripts/verify.py driver` passes, which needs the verification skill on main or committed before any product change. Mandatory: no skip-with-reason escape.
8. Implement. Delegate code-writing to one executor on the executor model from the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`): a native subagent when your agent can run that model, otherwise the **salvo** skill (`../salvo/SKILL.md`) with that one entry. Spawn it in the same message as step 9's verifier, because the scripts need only the plan. Brief it with:
   - The skeleton, when one exists: its first commit applies the skeleton's files for this change, and the skeleton is the contract. A deviation (a parameter, a type, a module the skeleton did not anticipate) stops the executor to report whether the skeleton was wrong, the requirement was missed, or the implementation overreaches; a public one needs the user's agreement and goes in the addendum.
   - The scope: file paths and the named data shape with its organizing structure, per the Model the Domain principle (`../principles/references/principles/model-the-domain.md`).
   - The success criteria: the plan's checks; a spec written to fail first for every unit-tier check, with the check id in its test title, because `verify.py units` records which spec proves which check; typecheck, lint, and `verify.py units` green before it hands back; comments per the **code-comments** skill (`../code-comments/SKILL.md`), then the **no-comments** skill (`../no-comments/SKILL.md`) on its own diff, because the author removes a comment cheapest. It writes no e2e script, because a script its author writes checks what the author meant to build.

   It commits as the work goes, in commits it would keep, because the history is never regrouped. When the implementation admits several valid shapes, delegate through the **arena** skill (`../arena/SKILL.md`) instead. Run one agent per worktree at a time, stopping the previous agent's task and running `verify.py leftovers --kill` before another touches it. When the same kind of friction keeps coming back (one workaround repeated across unrelated code, special cases for unrelated edges, types that need casts or always-set optionals, a lock the design said was not needed, callers that must know the internals), the design is wrong: stop, rerun the architect skill from what was learned, and subtract before adding, per the Subtract Before You Add principle (`../principles/references/principles/subtract-before-you-add.md`), instead of patching. Close this step only when `../verify/scripts/verify.py units` passes. Mandatory: no skip-with-reason escape, because the gain is review separation, not lines saved.
9. Write the e2e scripts, in parallel with step 8. Spawn the verifier from the **verify** skill's step 5 (`../verify/SKILL.md`), on a different executor-role entry from the code writer, in its own worktree at the phase's base: it writes one zero-argument `<id>.check.<ext>` per e2e-tier check from the plan, the skeleton, and the driver only, never the implementation, because a script written from the code checks the code. A perf check is such a script that measures main and head and compares against its Rule itself, and the blast-radius safety fact is one of these checks. When a check needs the driver to do more, the verifier extends the driver, commits it in its worktree, and you cherry-pick it onto the phase branch. Skip this step with the reason only when the plan has no e2e check.
10. Prove every check in the plan with the verify skill, once the code lands. Send the same verifier its prove stage: it runs `verify.py rerun` and `verify.py units`, walks every walk-tier check once on the real app with a screenshot or video in `evidence/<id>/`, and writes `report.md`, with the perf scripts run alone after the others. Collect the oracles' values as the verify skill says, and audit every evidence file the report names yourself. Close this step only when `../verify/scripts/verify.py oracles` passes. Mandatory: no skip-with-reason escape, because the author's own run is not a verdict.
11. Fix what failed. Group every FAIL by root cause and give each group to an executor, which fixes it at the root cause and grades the fix with `verify.py rerun --only <its ids>` and `verify.py units`; a fixed walk check goes back to the same verifier, resumed. Never spend a fresh verifier on a fix, because a saved script grades it without one, and guard allows one verifier per check. A check gets at most 2 failed fix attempts: once `report.md` marks it FAIL, `verify.py rerun --only` counts each failing run and then refuses it. Then take it to the user with its repro, what each fix changed, and the premise the fixes shared, per the Attack the Premise principle (`../principles/references/principles/attack-the-premise.md`), or in an autonomous run put it in the backlog with the fix you recommend and leave it FAIL. Update the report's rows and its Head from the graded results. Skip this step with the reason when nothing failed.
12. Explore with a fresh explorer, in every task, not only UI work: a subagent on a different executor-role entry from the code writer, briefed with the verify skill's `references/explorer-prompt.md`. It tries to break the change outside the listed checks for at most 20 minutes, with its evidence in `evidence/explore/`, because `verify.py report` refuses evidence there that spans longer, and an open-ended exploration grows the plan until no round is final. Triage every finding per the verify skill's step 11; a new check gets a tier and joins step 11 with the same fix budget. Mandatory: no skip-with-reason escape, because exploration finds what no planned check names.
13. Review the code with a fresh reviewer: a planner-role model from a different family through salvo when the config has one, else a different entry, briefed with the verify skill's `references/reviewer-prompt.md`. It reviews the phase diff adversarially for security, error paths, concurrency, multi-account state, and wire and back compatibility, and writes `review.md` in the verification directory, because it reads paths no check drives. Triage every finding there like an exploration finding; a real one becomes a new check with a tier and joins step 11. When an implementation choice is contested, also run the **interrogate** skill (`../interrogate/SKILL.md`). Mandatory: no skip-with-reason escape, because the `report` gate refuses a report without a triaged review.
14. Final run, then the PR. After the last code change, run `verify.py units` once more, because the report holds each unit check to a units run on the code that ships. Close this step only when `../verify/scripts/verify.py rerun` passes, `../verify/scripts/verify.py report` passes, and `../verify/scripts/verify.py leftovers` passes; the rerun stamp makes the repeat free when nothing changed since a passing full run. Run the **open-pr** skill (`../open-pr/SKILL.md`) on the commits as they were made, with no regroup and no per-commit runs, because the final run proves the tree that ships; in a stacked feature open it against the previous phase's branch. Never merge: the user lands every PR. Mandatory: no skip-with-reason escape.

Code-coupled work (one feature, one migration) goes to a single owner with the checkpoint inline. Parent-level fan-out is for slices that produce independent artifacts. Spawn a fresh owner rather than chaining interrupts, and a fresh executor for follow-up work rather than resuming a long one, because a resumed agent pays its whole context again on every call. Tell the user when each phase ends and what starts next.

**Reply:** what you built, what you chose and why, the throughput checkpoint, the verify skill's check table, every exploration and review finding with its triage, each item added to the backlog, and open decisions. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`, so every run is measured against the last.
