# Feature

**You own the design. Plan, review, verify.** Delegate implementation. Stay in the lead.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why.

**Keep the lead light.** Every lead turn resends the whole conversation, so the lead's context size multiplies the cost of every call it makes, and spent tokens turn into wall-clock time when the usage window runs out. When this session already carries a finished task (`../reflect/scripts/profile.py <transcript> --context` above 200k tokens), hand this task to a fresh owner subagent on your own model with a handoff brief, and only relay. Ask every subagent for a hand-back of at most 200 words with the details in a file you open only to audit. Pipe command output down to the lines you need, and mark todos in the same call that does the work. After spawning a background agent, end the turn or do other work, because its hand-back arrives on its own and guard lets a turn end while background work is pending. Never poll a transcript or a file for a subagent's completion: its final stop is a tool call, not `end_turn`, so such a loop runs to its cap after the agent is done.

1. Clarify the requirements and what proves them. Review the feature spec and list what it leaves open that the user will see or rely on: inputs, outputs and their format, behavior at the edges, and scope. Before the first question, read the spec's status line, the feature docs, and memory for decisions already deferred, and ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan and a question under a branch the user then cuts is a wasted round. Alongside it, draft the verification plan per `../verify/references/plan.md`, with perf acceptance, the seed data each check needs, and an oracle check for every value computed from data, because each pass predicate and budget states a requirement in checkable form. Each open item, predicate, and budget is a product decision, and making it yourself builds your guess instead of their feature, so discuss both with the user before designing. Settle an item a run can answer (a layout, a timing, which approach works) with the **prototype** skill (`../prototype/SKILL.md`) first, so the discussion is over evidence instead of guesses. A spec that settles every item, predicate, and budget needs no discussion. Size the process to the change: a perf check exists only for a path where the change adds work the user waits on or work that scales with data, and "not slower than main" on an untouched path is `n/a`, because measuring a path nothing could have moved spends a verifier on numbers nobody doubts. Record each dropped step with its reason. Then write the plan file. Do not copy its checks into the todo list, because the `report` gate already refuses a check without a verdict and every todo mark costs a lead turn. Close this step only when `../verify/scripts/verify.py plan` passes. Mandatory: no skip-with-reason escape, because every later step builds and verifies against this plan.
2. Read the **principles** skill (`../principles/SKILL.md`) and every principle file it indexes. Mandatory: no skip-with-reason escape, because the principles shape every later step and a citation is only honest when its file was read.
3. Run the **how** skill (`../how/SKILL.md`) over the affected subsystem. When a previous phase left a grounding document, hand it to how as the starting model and scope the explorers to what changed since, because re-deriving a mapped subsystem repeats finished work.
4. Settle the design shape. Decide which case holds and write it on the todo item, because the cases cost very different amounts:
   - **A: a design doc exists and still applies.** Diff it against the step 3 grounding and write a one-page addendum for what current code contradicts, what the doc leaves out, and any open decision. Skip the addendum when there is none. Run the **architect** skill (`../architect/SKILL.md`) only for a gap that is itself a structural decision, scoped to that gap with the doc as a fixed constraint.
   - **B: no doc, and the change follows existing patterns.** Write a short design note: types, module placement, data flow. No arena.
   - **C: no doc, and the architecture is novel or cross-cutting.** Run the architect skill in full, so its arena runs with the planner role's runners and efforts and the cross-judge kept, because one sketch presents a single shape with confidence.

   In every case, a product decision found in the gap goes back to the user as in step 1. When the change reaches past its diff (a shared primitive, a wire format, a schema, a flag), run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the design artifact (addendum, note, or sketch) before step 7, and fix the design for what it finds, because a risk found on paper costs a line and the same risk found after the code costs a fix wave. When candidates split on a premise a run can check, settle it with the **prototype** skill (`../prototype/SKILL.md`) instead of letting the judge guess. When the designs or a prototype show that a pass predicate is wrong or missing, revise the plan with the user per `../verify/references/plan.md`.
5. Write the throughput checkpoint as five todo items. A dimension that genuinely does not apply (single file, no fan-out) keeps its item with `n/a: <reason>` rather than being dropped:
   - **Blocking first steps.** Gates run before fan-out. Run the project's test suite on main once first, and give any pre-existing failure to exactly one owner, because otherwise every executor meets it and fixes it again.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize. Give each independent unit (one bug, one fix, one doc) its own executor instead of queueing several in one agent, because the slowest agent sets the wall-clock time and an agent's cost per call grows with everything it has already done. List every agent the run will spawn with its subscription and effort, because the lead, native subagents, and Claude runners share one usage window. Order the work so a limit hit finds work queued that needs another subscription or no agent (grounding reads, plan edits, evidence audit), instead of an idle wait.
   - **Shared mutable state.** Default to splitting the target (the Separate Before Serializing Shared State principle (`../principles/references/principles/separate-before-serializing-shared-state.md`)). Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
   - **Machine capacity.** Admit work by load, not by a fixed count. Before every spawn or instance start, run `../verify/scripts/verify.py capacity` (with `--native` for a native app build), which passes while the 1-minute load is under 0.7 x cores and no native build runs. Start instances one at a time and wait until each is ready before the next check, because the load average trails a start by about a minute. run perf runs and per-commit checks only while nothing else heavy runs, and rerun below load any failure that also fails on main under the same load before it counts, because overload makes false failures and slow drivers. When the load exceeds the cores, run `../verify/scripts/verify.py leftovers --kill` before attributing it: with nothing left to kill it lists the busiest processes with pid, ppid, elapsed time, and cwd, and a ppid-1 process older than the current step is a leftover to kill before any spawn, because orphans from earlier delegates are the usual cause and get blamed on the busy workers.
6. Get the driver before any code for this change exists. Use the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`). Without one, run the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) in a clean worktree off main, because a driver built after the change learns the change's behavior as the app's and stops catching its bugs. Close this step only when `../verify/scripts/verify.py driver` passes, which needs the verification skill on main or committed before any product change. Build it in its own worktree while step 7 runs in another, then rebase the change onto the driver commit, because the gate checks only the order in history. Mandatory: no skip-with-reason escape.
7. Delegate code-writing to a subagent on the executor model from the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`). Use a native subagent when your agent can run that model, otherwise the **salvo** skill (`../salvo/SKILL.md`) with that one entry, and apply its patch. Give it a specific scope (file paths, named data shape and its organizing structure per the Model the Domain principle (`../principles/references/principles/model-the-domain.md`), a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic, and success criteria: the plan's checks, with its unit tests written to fail first). When the implementation admits multiple valid shapes (error handling, abstraction layer, test structure), delegate via the **arena** skill (`../arena/SKILL.md`) instead so the runners surface the alternatives and the cross-judge guards the pick. Mandatory: no skip-with-reason escape, and Laziness Protocol does not override it (the gain is review separation, not lines saved). A subagent forbidden to spawn satisfies this by owning the diff directly with the same review separation. No "standing by" reply that waits on a nested agent. Comments per the **code-comments** skill (`../code-comments/SKILL.md`). Surgical edits, re-ground against the source for upstream-derived files. Port shared-primitive improvements to all consumers and verify each. Commit liberally. Have the executor run `../verify/scripts/verify.py units` before it hands back, so every spec it wrote is proven to fail on base and pass at head; a spec that passes on base goes in its own file containing the marker `regression-guard`. When the brief or a user decision changes a user-visible output after the plan is written, revise the touched predicate in the same turn (with `verify.py freeze --revision` once the plan is frozen), because a predicate written for the old output fails the new one. Run one agent per worktree at a time, and stop the previous agent's task (TaskStop, loaded with ToolSearch) before another agent touches that worktree, because its background shell jobs keep writing after it hands back, then run `../verify/scripts/verify.py leftovers --kill`, because TaskStop and a shell timeout end the shell, not its children. Have the executor save each plan check it touches as a `<id>.check.<ext>` script in the verification directory, runnable with no arguments (it provisions and tears down its own instance through the driver, because the gate runs `rerun` bare), with every wait bounded by a deadline taken from the predicate, and run `../verify/scripts/verify.py rerun` before it hands back, so the verifier reruns and audits those scripts instead of driving the same steps again. For follow-up work in the same area, spawn a new executor whose brief carries the earlier findings instead of resuming a long-running one, because a resumed agent pays its whole context again on every call. When the plan has native-app checks, start that app's instance in the background as soon as the executor starts and reuse it through the driver's sync, because a native build is the longest wait in a round.
8. Prove every check in the plan with the **verify** skill (`../verify/SKILL.md`). First run the **no-comments** skill (`../no-comments/SKILL.md`) on the executor's diff, because the freeze and the one rewrite in step 9 must not be followed by a comment cleanup. Then rewrite the throughput checkpoint for verification: which verifiers run in parallel on their own instances, within the Machine capacity cap with `uptime` checked before every spawn, and which must wait, such as perf. Before the first verifier, measure every perf budget in the plan once yourself, and when step 4 ran blast-radius, re-prove its one safety fact on the real code; fix what either finds first, because a verifier round spent on a change that a cheap check would have reshaped is wasted. Then a fresh verifier drives the change on its matching surface, such as a CLI in a real terminal or a web UI in a real browser through chrome-devtools-axi, and you audit its evidence. Mandatory: no skip-with-reason escape, because the author's own run is not a verdict. "Inconclusive" or wrong-surface is not a pass. Flag it. Close this step only when `../verify/scripts/verify.py report` passes, `../verify/scripts/verify.py rerun` passes, and `../verify/scripts/verify.py leftovers` passes, which also keeps a verifier from spawning on top of an earlier one's survivors. Collect every FAIL and every finding triaged as a new check in a round, group them by root cause and delegate each group's fix at its root cause, one executor per group in parallel within `capacity`, so a shared cause is fixed once and independent ones do not queue, have it run `rerun` and `units` before it hands back, then run the verify skill as a fix-wave round: a fresh verifier drives only the fixed checks and the checks the fix's diff maps to, while `rerun` and `units` are the regression net for the rest. One fix wave per round, not one per finding. Tell the user when each phase ends and what starts next, so they never have to ask for progress.
9. Group the executor's commits once into small, ordered commits from the files step 8 left clean, all in one PR with no stack, because every rewrite repoints every later branch and history carries no evidence. Run `../verify/scripts/verify.py units` once on the result: the plan's Unit check is graded by it, never by commit order, so spec and fix may share a commit. Check every commit with `python3 ../verify/scripts/verify.py commits <base>..<head> --typecheck '<typecheck command>' --cmd '<test command>'` in the foreground, never as a hand-written loop or a background job, because it runs one commit at a time in a scratch tree under a timeout, kills whatever a commit leaves running, and prints one PASS or FAIL per commit (a failing spec-only commit reports without failing the run).
   Use the Sequence Work into Verifiable Units principle (`../principles/references/principles/sequence-verifiable-units.md`), building, verifying, and committing each small unit before the next.
10. If the design is contested, run the **interrogate** skill (`../interrogate/SKILL.md`) before shipping.
11. Run the **open-pr** skill (`../open-pr/SKILL.md`).

Code-coupled work (one feature, one migration) goes to a single owner with the checkpoint inline. That owner fans out internally after the blocking phase. Parent-level fan-out is for slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments). Rewrite the checkpoint at phase boundaries. Spawn a fresh owner rather than chaining interrupts. A bug fixed on sight is its own artifact: its own worktree, its own branch off main, its own PR, and never in the feature's base unless the feature cannot be verified without it, because stacking it under the feature failed shared-database checks and forced a re-freeze. Run each such bug, and each follow-up bug, through the **bug-fix** skill (`../bug-fix/SKILL.md`), one executor per bug.

**Reply:** what you built, what you chose and why, the throughput checkpoint, the verify skill's check table, every exploration finding with its triage, open decisions. Tables for design alternatives. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`: wall time, idle time, agents, and tokens, so every run is measured against the last.
