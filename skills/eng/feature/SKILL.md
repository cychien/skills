# Feature

**You own the design. Plan, review, verify.** Delegate implementation. Stay in the lead.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

This is the tier for big work. A change that fits one PR and copies a pattern the code already has belongs to the **quick-feature** skill (`../quick-feature/SKILL.md`), unless the user asked for this one. A feature that spans several PRs or is too vague to build is planned first by the **plan-feature** skill (`../plan-feature/SKILL.md`); point this skill at its plan folder and build each phase per `references/phases.md`.

Open a todolist whose first items are the steps below, copied in verbatim, before any task-specific todos. The `guard` skill's `todo from feature` does this; without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why.

**Keep the lead light.** Every lead turn resends the whole conversation, so the lead's context size multiplies the cost of every call. When this session already carries a finished task, or the lead passes 200k tokens of context at a phase boundary (`../reflect/scripts/profile.py <transcript> --context`), hand the rest to a fresh owner subagent on your own model with a handoff brief, and only relay. Ask every subagent for a hand-back of at most 200 words with the details in a file you open only to audit. Pipe command output down to the lines you need, and mark todos in the same call that does the work. After spawning a background agent, end the turn or do other work, because its hand-back arrives on its own; guard denies polling for it.

**No blocking, no detours.** In an autonomous run, start it with the `autorun` skill's `--backlog <project backlog>` (such as `docs/backlog.md`), so a reversible question the reviewer cannot settle lands in the backlog with your pick and the run goes on with it. A bug or idea found on the way that this feature does not cause and that no check depends on goes to that backlog with its repro and where it came from, never into this diff, because each such fix starts another verify loop. Fix one here only when a check of this feature cannot pass without it, as its own PR through the **bug-fix** skill (`../bug-fix/SKILL.md`).

1. Clarify the requirements and what proves them. With a plan folder from the plan-feature skill, the decisions and this phase's plan are settled: run `python3 ../verify/scripts/verify.py adopt <plan folder>/phases/<phase>` on the phase's fresh branch, and ask only what the plan leaves open. Otherwise review the spec and list what it leaves open that the user will see or rely on: inputs, outputs and their format, behavior at the edges, and scope. Read the spec's status line, the feature docs, and memory for decisions already made, and ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the plan. Draft the verification plan per `../verify/references/plan.md` alongside: perf acceptance, the seed data each check needs, and an oracle check for every value computed from data. Each open item, predicate, and budget is a product decision, so discuss them with the user in one round before designing. Settle an item a run can answer with the **prototype** skill (`../prototype/SKILL.md`) first. A perf check exists only for a path where the change adds work the user waits on or work that scales with data. Do not copy the plan's checks into the todo list, because the `report` gate already refuses a check without a verdict. Close this step only when `../verify/scripts/verify.py plan` passes. Mandatory: no skip-with-reason escape, because every later step builds and verifies against this plan.
2. Read the **principles** skill (`../principles/SKILL.md`) and every principle file it indexes. Mandatory: no skip-with-reason escape, because the principles shape every later step and a citation is only honest when its file was read.
3. Run the **how** skill (`../how/SKILL.md`) over the affected subsystem. When a plan folder or an earlier phase left a grounding document, hand it to how as the starting model and scope the explorers to what changed since; when it already covers every subsystem this change touches, close this step with `--not-run how` and that reason.
4. Settle the design shape. Decide which case holds and write it on the todo item, because the cases cost very different amounts:
   - **A: a design and its skeleton exist and still apply** (a plan folder, or a design doc). Diff them against the step 3 grounding and write a one-page addendum for what current code contradicts and any open decision; skip the addendum when there is none.
   - **B: no design, and the change follows existing patterns.** Write a short design note: types, module placement, data flow.
   - **C: no design, and the architecture is novel or cross-cutting.** Run the **architect** skill (`../architect/SKILL.md`), saving `skeleton.patch` and its rationale in the verification directory, then add a conformance check to the plan whose `- Skeleton:` field names the files and symbols this change implements and whose Pass is that the implemented signatures match the skeleton or each difference is in the addendum with the user's agreement.

   A product decision found here goes back to the user as in step 1. Without a plan folder that already did it, run the **blast-radius** skill (`../blast-radius/SKILL.md`) on the design artifact when the change reaches past its diff (a shared primitive, a wire format, a schema, a flag other code reads), fix the design for what it finds, and add its safety fact to the plan as a check, because a risk found on paper costs a line. When candidates split on a premise a run can check, settle it with the prototype skill.
5. Lock the plan before any code exists. Close this step only when `../verify/scripts/verify.py lock` passes: it refuses once product files have changed, and afterwards every change to a check or budget needs `verify.py freeze --revision` naming who agreed, because a predicate edited after the code was seen describes the code. Mandatory: no skip-with-reason escape.
6. Write the throughput checkpoint as five todo items. A dimension that does not apply keeps its item with `n/a: <reason>`:
   - **Blocking first steps.** Run the project's test suite on main once first, and give any pre-existing failure to exactly one owner, because otherwise every executor meets it and fixes it again.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize; shared writes serialize. Give each independent unit its own executor, because the slowest agent sets the wall-clock time and an agent's cost per call grows with everything it has done. List every agent the run will spawn with its subscription and effort, because they share one usage window.
   - **Shared mutable state.** Default to splitting the target, per the Separate Before Serializing Shared State principle (`../principles/references/principles/separate-before-serializing-shared-state.md`). Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
   - **Machine capacity.** Before every spawn or instance start, run `../verify/scripts/verify.py capacity` (with `--native` for a native build), which passes while the 1-minute load is under 0.7 x cores and no native build runs. Start instances one at a time. Run perf and per-commit checks only while nothing else heavy runs. When the load exceeds the cores, run `../verify/scripts/verify.py leftovers --kill` before blaming the busy workers, because orphans from earlier delegates are the usual cause.
7. Get the driver: the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`). Without one, run the **create-verification-skill** skill (`../create-verification-skill/SKILL.md`) in a clean worktree off main, because a driver built after the change learns the change's behavior as the app's. Close this step only when `../verify/scripts/verify.py driver` passes, which needs the verification skill on main or committed before any product change. Mandatory: no skip-with-reason escape.
8. Delegate code-writing to a subagent on the executor model from the orchestrator config (`<project>/.agents/orchestrator/models.json`, falling back to `~/.agents/orchestrator/models.json`): a native subagent when your agent can run that model, otherwise the **salvo** skill (`../salvo/SKILL.md`) with that one entry. Brief it with:
   - The skeleton, when one exists: its first commit applies the skeleton's files for this change, and the skeleton is the contract. A deviation (a parameter, a type, a module the skeleton did not anticipate) stops the executor to report whether the skeleton was wrong, the requirement was missed, or the implementation overreaches; a public one needs the user's agreement and goes in the addendum.
   - The scope: file paths and the named data shape with its organizing structure, per the Model the Domain principle (`../principles/references/principles/model-the-domain.md`).
   - The success criteria: the plan's checks, unit specs written to fail first, comments per the **code-comments** skill (`../code-comments/SKILL.md`), and each check it touches saved as a zero-argument `<id>.check.<ext>` script in the verification directory with every wait bounded by the predicate's deadline.

   It runs `../verify/scripts/verify.py units` and `../verify/scripts/verify.py rerun` before it hands back, so its own drive of the real surface catches the plain mistakes before a verifier is spent. When the implementation admits several valid shapes, delegate through the **arena** skill (`../arena/SKILL.md`) instead. Run one agent per worktree at a time, stopping the previous agent's task and running `verify.py leftovers --kill` before another touches it. When the same kind of friction keeps coming back (one workaround repeated across unrelated code, special cases for unrelated edges, types that need casts or always-set optionals, a lock the design said was not needed, callers that must know the internals), the design is wrong: stop, rerun the architect skill from what was learned, and subtract before adding, per the Subtract Before You Add principle (`../principles/references/principles/subtract-before-you-add.md`), instead of patching. Mandatory: no skip-with-reason escape, because the gain is review separation, not lines saved.
9. Prove every check in the plan with the **verify** skill (`../verify/SKILL.md`), once. First run the **no-comments** skill (`../no-comments/SKILL.md`) on the diff, measure every perf budget yourself, and re-prove the blast-radius safety fact on the real code when there is one; fix what these find first, because a verifier spent on a change a cheap check would have reshaped is wasted. Then one full round: fresh verifiers, each naming the check ids it grades, drive every check on its real surface and explore, within `capacity`, and you audit their evidence. Group every FAIL by root cause and give each group to one executor, which runs `verify.py rerun --only <its ids>` and `units`; then one fix wave: a fresh verifier drives only the fixed checks and the checks their diff maps to, while `rerun` and `units` regrade the rest. A check still failing after its fix wave goes to the user with its repro and what each fix changed, or in an autonomous run into the backlog with the fix you recommend, the check left FAIL; guard denies a third verifier for it. Close this step only when `../verify/scripts/verify.py report` passes, `../verify/scripts/verify.py rerun` passes, and `../verify/scripts/verify.py leftovers` passes. Mandatory: no skip-with-reason escape, because the author's own run is not a verdict.
10. Group the commits once into small, ordered commits from the files step 9 left clean, per the Sequence Work into Verifiable Units principle (`../principles/references/principles/sequence-verifiable-units.md`). Run `../verify/scripts/verify.py units` once on the result, and check every commit with `python3 ../verify/scripts/verify.py commits <base>..<head> --typecheck '<typecheck command>' --cmd '<test command>'` in the foreground, where base is main, or the previous phase's tip in a stacked phase.
11. When an implementation choice is contested, run the **interrogate** skill (`../interrogate/SKILL.md`) before shipping.
12. Run the **open-pr** skill (`../open-pr/SKILL.md`). Never merge: the user lands every PR.

Code-coupled work (one feature, one migration) goes to a single owner with the checkpoint inline. Parent-level fan-out is for slices that produce independent artifacts. Spawn a fresh owner rather than chaining interrupts, and a fresh executor for follow-up work rather than resuming a long one, because a resumed agent pays its whole context again on every call. Tell the user when each phase ends and what starts next.

**Reply:** what you built, what you chose and why, the throughput checkpoint, the verify skill's check table, every exploration finding with its triage, each item added to the backlog, and open decisions. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`, so every run is measured against the last.
