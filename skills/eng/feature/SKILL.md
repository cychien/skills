# Feature

**You own the design and the code. A reviewer from another model family reads it before it ships.** Build it yourself, because every hand-off costs a start and a brief. Spend the second opinion where it pays: a cross-family review finds the security, concurrency, failure-path, and cross-account defects that tests and a run on the real surface miss.

Paths like `../how/SKILL.md` point to skills installed beside this one, relative to this file's folder.

This is the tier for work that needs a design or reaches past its diff. A change that copies a pattern the code already has belongs to the **quick-feature** skill (`../quick-feature/SKILL.md`), unless the user asked for this one. A feature that spans several PRs or is too vague to build is planned first by the **plan-feature** skill (`../plan-feature/SKILL.md`).

**With a plan folder** from the plan-feature skill, build every phase that has not landed, in its order, in this one session. Run the steps once per phase, starting each phase with a fresh `todo from feature`. Read `plan.md` (its Decisions, the phase's entry, and the Acceptance items it proves) and `spec.md` before each phase. When the code has to differ from `spec.md`, change it and the later phase entries the change affects, with a line in its `## Change log` naming the phase, what changed, why, and the phases it affects. Log design changes only, never implementation detail, so the log stays worth reading. Open one PR per phase, the first against main and each later one against the phase before it.

Open a todolist whose first items are the steps below, copied in verbatim. The `guard` skill's `todo from feature` does this and orders the steps: step 5 opens with step 4, and step 6 waits for both. Print each step with guard's `todo show <n>` before you work it, and close it with the token that prints. Without guard, use your agent's todo tool. A step you choose not to do stays in the list with a one-line `skip: <reason>`, so the user sees what was skipped and why.

**Usage limits never block.** Pick the reviewer with `python3 ../guard/scripts/guard.py quota pick --role planner --avoid <your agent>` (such as `--avoid claude`), which skips every entry of your own family and every subscription whose usage limit has not reset. When no entry of another family is free, `quota pick --role planner --avoid <your agent> --relax` gives the next one: name who reviewed instead of whom, and why, in the PR's Verification section and the reply.

**Time asks, it never kills.** No job is stopped because it ran long. Before you start background work (the reviewer through salvo, a dev server, a long build), start guard's watchdog, `python3 ../guard/scripts/guard.py watch`, as a background job of your own, and start it again after each report it ends with: it asks you about a job that went silent and costs nothing while jobs progress. Read the job's output and processes before you act, stop a stuck one with your agent's task-stop tool, and acknowledge a process meant to idle with `python3 ../guard/scripts/guard.py watch --ack <pid>`. Guard holds your turn while background work runs and no watchdog watches it.

**No blocking, no detours.** In an autonomous run, start it with the `autorun` skill's `--backlog <project backlog>` (such as `docs/backlog.md`), so a reversible question the reviewer cannot settle lands in the backlog with your pick and the run goes on with it. A bug or idea found on the way that this feature does not cause goes to that backlog with its repro and where it came from, never into this diff. Fix one here only when this feature cannot work without it, on its own branch cut from main and as its own PR through the **bug-fix** skill (`../bug-fix/SKILL.md`).

1. Clarify, and settle what proves it. Fetch main and cut a fresh branch and worktree from its latest tip, or with a plan folder from the previous phase's tip while its PR is open, and run `python3 ../verify/scripts/verify.py base` there (with the previous phase's branch when this phase stacks on it) until it passes, because a stale base turns every later diff and run into a comparison with old code. Run the project's test suite there once, so a pre-existing failure is known before it looks like yours. Read the spec, the feature docs, the backlog, and memory for decisions already made. Ask the scope and which-layer-owns-it questions first and alone, because one ownership answer can cut half the work, then every other open item the user will see or rely on (inputs, outputs, edges, failure behavior) together in one round. With a plan folder, the decisions are settled: ask only what the plan leaves open. Settle a question a run can answer with the **prototype** skill (`../prototype/SKILL.md`) instead of asking. Then write down what proves the change, in user terms, each fact at the cheapest level that can prove it, per the Prove at the Cheapest Level principle (`../principles/references/principles/prove-at-the-cheapest-level.md`): the behaviors to drive on the real surface; an oracle for every value computed from data, the expected value computed apart from the code under test (such as a query over seeded data) with seeds shaped at the edges (a month's last day, an empty set, a tie), because unit tests and a normal drive miss exactly those; and the perf decision, a budget only for a path where the change adds work a user waits on or work that grows with data, measured at production scale per the **benchmark-checklist** skill (`../benchmark-checklist/SKILL.md`). Present the predicates and budgets with the open items, because each is a product decision.
2. Design. Read the code the change runs through, with the **how** skill (`../how/SKILL.md`) when it spans subsystems you do not know. With a plan folder, the design is `spec.md` and the skeleton files the phase's entry names; resolve what the code as it is now contradicts. Otherwise write a short `design.md` in the verification directory that `python3 ../verify/scripts/verify.py where` prints: the data shape and who owns it, per the Model the Domain principle (`../principles/references/principles/model-the-domain.md`), module placement, data flow, failure behavior, and the names the change adds. When the architecture is novel or cross-cutting, run the **architect** skill (`../architect/SKILL.md`) and build against its skeleton. Read the principles index (`../principles/SKILL.md`), pick the principles the design applies, and read each one's file before you cite it. Run the **blast-radius** skill (`../blast-radius/SKILL.md`) when the design changes a wire format, a schema, a shared primitive, or a flag other code reads, fix the design for what it finds, and add its safety fact to what proves the change. Name the Sensitive paths, where a defect costs most (auth, permissions, crypto, money, data another account owns), because the reviewer reads them hardest. A product decision found here goes back to the user as in step 1.
3. Build it, with its tests. Write the code yourself, committing as you go in commits you would keep, because the history is never regrouped. Write unit specs with literal expected values for the behavior the change adds or alters, and the oracle and perf checks step 1 named. Run only the specs you touch while you develop, then lint, typecheck, and the project's whole unit suite once. Comment per the **code-comments** skill (`../code-comments/SKILL.md`), then run the **no-comments** skill (`../no-comments/SKILL.md`) on your own diff. When the same kind of friction keeps coming back (one workaround repeated across unrelated code, types that need casts or always-set optionals, callers that must know the internals), the design is wrong: stop, redesign from what you learned, and subtract before adding, per the Subtract Before You Add principle (`../principles/references/principles/subtract-before-you-add.md`), instead of patching.
4. Run it where the user meets it. Drive every behavior step 1 named once on the real app, through the project's verification skill (`.agents/skills/verify-<app>/` or `.claude/skills/verify-<app>/`) when there is one, else directly (the browser, a terminal, curl), and keep a screenshot or a transcript for the PR. Run it from the committed tree, because an ignored or uncommitted file passes in the working tree and ships missing. When the change ships in something users install or build (a published package, a generated project, an app bundle, a production build), run it once more from that artifact installed fresh (a local registry, a clean checkout, an empty home directory), because a run inside the dev tree hides what the artifact leaves out. Judge the flow as its user would, every prompt, wait, and dialog it adds, and show the user anything that feels wrong with its evidence, because no test asks whether a flow is acceptable. Fix what fails at its root cause, with a unit spec wherever one can see it. Skip this step with the reason only when nothing a user runs or installs changed.
5. Review across model families. Starts after step 3. Start a fresh reviewer from the **verify** skill's reviewer prompt (`../verify/references/reviewer-prompt.md`) in Mode `change`, through the **salvo** skill (`../salvo/SKILL.md`) from the worktree, on the entry the reviewer's `quota pick` gave, because a reviewer of the author's family shares its blind spots. Brief it with the design (`spec.md` or `design.md`) as the plan, and the Sensitive paths. Triage every finding: reproduce it or follow its reasoning, and end its line in `review.md` with `Triage: fixed`, `follow-up`, `pre-existing`, or `dismissed` and the reason. A finding is `fixed` only when the change caused it and data is wrong, behavior is wrong, or the user is blocked; fix it at its root cause, prove the fix with a unit spec, and drive again what it changes on the real surface. A follow-up or pre-existing finding goes to the backlog with its repro, so it ships unfixed in the open instead of starting another loop. Then send the same reviewer Mode `fix` on the diff from the Head it read to the head, once and always, even when nothing was fixed, because fixes bring their own defects and step 4's fixes can land after the first review. Triage it the same way, prove each fix it needs with a unit spec, and stop there with no third round. Once those fixes land, write `Fixed at: <sha>` in the `## Fix review` section, the commit that holds them, or its Head when nothing was fixed. When the same reviewer cannot take the fix review (its quota ran out), the next `quota pick --relax` entry does, and you add `Relaxed: <reason>` to the section. Close this step only when `../verify/scripts/verify.py review` passes. Mandatory: no skip-with-reason escape, because review finds what no test or run reaches.
6. Close, then the PR. After the last code change, run the project's whole unit suite once more, because a change can break a spec it never touched. Reconcile the design with what ships: with a plan folder, `spec.md` describes the shipped behavior; without one, `design.md` matches the code. Run the **open-pr** skill (`../open-pr/SKILL.md`) on the commits as they were made, with the step 4 screenshot or transcript and every review finding with its triage in the Verification section, against main or, with a plan folder, the previous phase's branch. Never merge, because the user lands every PR. Close this step only when `../verify/scripts/verify.py review` passes, which holds HEAD to the reviewed code, so a product change after the fix review goes back to the reviewer. Mandatory: no skip-with-reason escape.

With a plan folder, tell the user when the last phase's PR is open, with the stack in landing order.

**Reply:** what you built, what you chose and why, the reviewer and any quota relaxation, every review finding with its triage, how you ran it (and from which installed artifact), each item added to the backlog, and open decisions. Write it per the **reply** skill (`../reply/SKILL.md`). End with the run's profile from `../reflect/scripts/profile.py <transcript> --since '<first words of the task prompt>' --record <task label>`, so every run is measured against the last.
