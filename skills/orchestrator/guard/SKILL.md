name: guard
description: Hard rules that enforce skill conventions through hooks, so an agent cannot skip them - a todo list every item of which must resolve in its steps' order, one per agent, a read token per step, check-script gates on playbook steps, one verifier per check, foreground delegates from subagents, short hand-backs, no waits that match themselves or poll a verify run, a watchdog that asks the lead about silent background jobs and never stops one, no delegate work left running after its hand-back, a shared usage-limit registry that hands work to the next model, no em dash in replies, and the open-pr PR rules. Use when a guard message blocks you, to manage the todo list, or to add, change, or debug a guard rule.

# Guard

An instruction in a skill fails silently when an agent skips it. Guard moves the rules that can be checked mechanically into hooks, where skipping one blocks the agent and names the fix. A guard message is the rule speaking, not an error to work around.

## Rules

- **Todo list.** The agent decides what goes in the todo list, as in pstack: usually a skill's steps copied in verbatim, then task-specific items. Guard holds it to the list. Once a list exists, the turn cannot end while an item is open, except to ask the user a question or while background work is pending. To end the turn on a plain-text question (for example after the user declined a question tool and asked you to clarify), first mark the items that wait on the answer with `todo wait <n> --reason "<what the user must answer>"`: the turn may end once every open item is waiting, and waiting items reopen when the user's next prompt arrives. In an autonomous run `todo wait` is refused, because questions go through `autorun.py ask`, until `ask` escalates one to the user: while the run has a gate waiting on the user, `todo wait` works, so the turn ends on that question instead of looping the stop hook. In a non-interactive `claude -p` session the background shells and subagents its stop payload lists count as pending too, because it waits for them and resumes the lead with their results; a scheduled cron alone does not, because it exits when the turn ends with only a cron left, so the cron never fires. Agents whose stop payload lists no in-flight work (`codex exec` among them) show guard no pending work, interactive or not. An item whose text says "Mandatory" cannot be skipped. Skipping an item that would run another skill also skips that skill's items. After three stops in a row with no progress in between, guard lets the turn end, so a stuck run cannot loop forever, unless a Mandatory item is open: that one holds until it closes, and the only way out is a question to the user that names what blocks it.
- **Order.** `todo from` gives each item the steps it waits on: by default the step before it. A step that says "in parallel with step N", "beside step N", or "in the same message as step N" waits on what N waits on, so the two open together, and a step that says "Starts after step N" (or "steps N and M", "N, M and K") waits on exactly those. When a parallel pair is followed by a step with no such phrase, that step waits on both. `todo done` refuses an item while a step it waits on is open or waiting and names it; skipped and done steps count as resolved. Items from `todo add` wait on nothing and nothing waits on them. The list shows `[after <n>]` beside an item still waiting.
- **Read before done.** `todo show <n>` prints an item's full text, then the principles it names: for `../principles/SKILL.md` the principles index, for each `../principles/references/principles/<x>.md` that file. Its last line is `token: <6 hex>`, a hash of the text and those attachments. An item copied from a skill closes only with `todo done <n> --token <token>`, so a wrong or stale token (the skill or a principle file changed) refuses with the command to show it again. Showing a principle file counts as reading it.
- **Timed waits.** `todo hold --until <HH:MM or ISO time> --reason "..."` lets a turn end with open items until that time, for a usage limit that resets at a known time or a long external job; it expires on its own. A bare HH:MM means its next occurrence. The hold belongs to its list: `todo clear`, or a new item that archives a resolved list, ends it. In an autonomous run, autorun's stop hook honors the hold too, so the turn ends instead of looping until the limit resets.
- **Own lists.** Each subagent keeps its own todo list, apart from the lead's in the same session, so a delegate's `todo from` never adds its items to the lead's list. A subagent adds `--agent <its agent id>` to every todo command; guard denies a subagent's todo command without it and names the id. The lead's stop checks only the lead's list, and a subagent's stop holds only on its own.
- **Gates.** An item whose text names a skill's check script in backticks, as in `` `../verify/scripts/verify.py plan` `` or `` `../verify/scripts/verify.py plan --checks` `` (argument words and valueless flags only), can be marked done only when guard runs that script from the agent's working directory and it exits 0. A failing gate prints the script's output and keeps the item open, so a playbook step backed by a check cannot be closed on the agent's word.
- **Todo decision.** When the agent is about to follow a skill that has steps, whether the user invoked it by `/name` or a switchboard led the agent to it, tool calls stay held until the agent decides the list: copy the skill's steps, add its own items, or record that it needs none. Only a command that runs `guard.py todo` or `autorun.py start` or `mode` counts as deciding, not the same words in a comment or inside another command's quoted argument. A switchboard without steps asks nothing, so the decision falls on the playbook it leads to. Reading a `SKILL.md` counts as following that skill when the file sits under a skill root (`.agents/skills`, `.claude/skills`, and their home-directory counterparts) or outside the current git working tree; a skill's own source inside the working tree is being authored, so reading it asks nothing. A read that only satisfies an open item's citation asks nothing; a `/name` invocation or a Skill tool load still does.
- **Short hand-backs.** A subagent whose final message, or SubagentHandback message, is longer than 300 words (a CJK character counts as half a word) is sent back once: put the details in a file and hand back at most 200 words with the file path. The same message sent again goes through, so an agent type that cannot write files is not looped. That pass lasts until the delegate ends, so a resumed agent's next long hand-back is sent back again.
- **One rerun after every fix.** A shell command that runs `verify.py rerun` (with or without `--only`), directly or in the program a shell runs with `-c` or `eval` runs, is denied while the session tracks a running subagent other than the caller, because a fix group still working would make the run grade half its fixes. The denial names the subagents it waits on, and a delegate that gets it stops and reports to the lead instead of retrying.
- **PR at the close step.** `gh pr create`, directly or through `bash -c`, `sh -c`, `env`, or `eval`, is denied while the lead's list holds an item from a skill that names `../open-pr/SKILL.md` and an earlier item from that skill is still open or waiting.
- **Usage limits.** Guard keeps a registry of limited subscriptions in `~/.agents/orchestrator/limits.json` (`ORCHESTRATOR_HOME` overrides the folder), one entry per agent (`claude`, `codex`) with `until`, `seen`, and `source`; an expired entry is ignored. It records a limit only when a shell command that runs `codex` or `claude -p` exits non-zero with that agent's limit message in its output (Claude Code reports such a command through its PostToolUseFailure hook), and salvo records the limits its runs hit. A subagent's result, a log, or any other output that quotes a limit message records nothing. A shell command that starts a limited agent (`salvo.py run` with its entry, or `codex exec`) is denied with the next candidate for each role. A native Agent spawn is not checked, because it runs on the lead's own subscription.
- **Reserved subscriptions.** When the branch's verification plan (`verify.py where`, then the plan it holds or the adopted phase plan) has a check with a `- Agent: real` line, the agents those checks drive, other than the lead's own, are reserved for them: `salvo.py run` or `codex exec` on one is denied with a `quota pick --avoid` alternative, except in a check script run (`verify.py rerun`). A check names the agents it drives in its own text, else the plan's preamble does; naming none reserves every agent. The plan is read where the command runs: the directory a leading `cd <dir> &&` or `cd <dir>;` moves it to, else the agent's working directory, so a launch into another worktree answers to that worktree's plan. When the plan cannot be found, or a leading `cd` goes where only the shell knows (`cd -`, a variable, a substitution, a glob), nothing is reserved, because a false deny stops every agent while a missed reservation costs one run's quota.
- **No em dash.** A reply with an em dash outside code is sent back for a rewrite. This holds in every session.
- **Tracked salvo.** A shell command that runs `salvo.py run` detached with `nohup` or a trailing `&` is denied, because the harness then never notifies the agent when it ends. Run it in a background tool call instead. Text inside quotes or a heredoc does not count. This holds in every session.
- **Filled templates.** A subagent prompt (the Agent tool's prompt, or the file a `salvo.py run` reads on stdin) that starts from a skill's `references/*-prompt.md` template is denied while it still holds one of that template's fills, any `<...>` containing a space. This holds in every session.
- **One verifier per check.** A spawn whose prompt starts from the verify skill's verifier prompt is denied for a check that already had a verifier that wrote evidence for it. Its `<id>.check.<ext>` scripts, written before the code lands, are not that evidence, so the same verifier can come back for its prove stage. A fix is graded by `verify.py rerun --only` and `verify.py units`, which count its failed fix attempts, never by another verifier.
- **Foreground delegates.** A subagent that spawns an agent with `run_in_background` is denied, because the harness kills a subagent's background children when its turn ends. Run it in the foreground; for parallel work, put several foreground Agent calls in one message. The lead may still spawn in the background.
- **Leftover sweep.** After a TaskStop call, guard runs the **verify** skill's `verify.py leftovers --kill` and shows the agent its output. A spawn (the Agent tool) is denied with the sweep's output while `verify.py leftovers` still lists survivors, because a new delegate on top of an old one's processes hides which one caused any later problem. A process can be a running delegate's own instance or browser bridge, so guard tracks each subagent as running from its SubagentStart (or, where the agent has no such hook, its first tool call) until its stop goes through, its task is stopped, the lead's turn ends with no background work, or it calls no tool for 20 minutes (twice the Bash timeout); a resumed one starts again. Once a SubagentStart reached the session, an agent id that never started is no delegate: Claude Code's memory extraction runs as a forked helper that calls tools under its own id but never starts, writes a transcript, or stops, and counting it held reruns and sweeps for hours. `autorun.py install` registers SubagentStart. `guard.py delegates` lists each one's state, and only the lead ends one it confirmed gone with `guard.py delegates end <id> --reason`. Guard passes the sweep `--running-since` the start of the earliest one other than the caller: a process started since then is listed as in use by a running agent, never counted against the spawn and never killed. When the verify skill is not installed or the sweep cannot run, the spawn is allowed and the reason goes to `errors.log` in the guard state folder.
- **No polling for subagents.** After the session spawns a subagent, a shell command that loops with a sleep while reading a task output file (`/tasks/<id>.output`) or grepping for `stop_reason` or `end_turn` is denied. A subagent's hand-back arrives on its own as a message, and it finishes with a SubagentHandback call, so such a loop never matches and runs to its cap. This holds in a non-interactive `claude -p` session too, which waits for a background subagent and resumes the lead with its hand-back. Ordinary sleeps for servers or builds are not affected.
- **No polling for verify runs.** A shell command whose `while` or `until` loop sleeps and waits on a `verify.py rerun` or `verify.py dryrun` is denied: when a command that decides whether the loop ends, its condition or a body command chained to a `break` or `exit` or testing an `if` that breaks, names its process, by text another command matches (`pgrep -f`, `ps | grep`), or its output file, by a name with `rerun` or `dryrun` in it or the file the run's own redirect writes in the same command. Run it in a background tool call; its completion notification arrives on its own. A body command that only mentions such a file decides nothing, and a loop that runs the script itself does not wait on it. This holds in every session.
- **No self-matching process waits.** A shell command that runs `pgrep -f` or `pkill -f` with a pattern that matches the command line holding it is denied, because the shell running the command carries that line: a wait on the pattern never ends and a kill hits the shell itself. Wait on a marker the job writes, or bracket one character of the pattern (`[v]erify.py`) so it matches only other processes. Without `-f`, pgrep matches process names only and is not affected. This holds in every session.
- **Watchdog required.** When the lead ends its turn while background work runs on this machine (a shell, a monitor, a subagent, or a workflow in the stop payload's in-flight list) and no watchdog of its session is alive, the stop is blocked with the command that starts one, `guard.py watch`, as a background job of the lead's own. A session with no background work is never asked. Only an agent whose stop payload lists its in-flight work can be checked (Claude Code's does); elsewhere the playbook's prose asks for the watchdog. After three such blocks the turn may end until the user's next prompt, so a lead that cannot start one is not looped, and a session where the watchdog found no agent process to watch is not held. In a non-interactive session, a stop whose only in-flight work is the watchdog stops the watchdog, because `claude -p` waits for its background shells and the watchdog waits for the agent to exit, so the session would otherwise wait forever.
- **No work outlives its hand-back.** Guard records each background task a subagent starts (the task id its shell tool returns) and each hand-back (a SubagentHandback call that delivered, or a subagent stop that went through). While the lead's stop payload lists in flight a delegate that handed back, or a task such a delegate started, the lead's stop is blocked with each task's id, so the lead stops it with its task-stop tool. A delegate resumed by a SubagentStart or by a lead message that names it has not handed back. The payload names in-flight tasks by id, a subagent's task id is its agent id, and a delegate's background shell outlives its SubagentHandback, so the check sees exactly the leftover work; an agent whose stop payload lists no in-flight work is not checked.
- **Reply.** When a skill in the todo list asks for its reply per the **reply** skill, the turn cannot end after the list resolves until that skill was read.
- **PR rules.** Once a session uses the **open-pr** skill, `gh pr create` and `gh pr edit` are checked before they run: a Conventional Commits title with no trailing period, no `--draft`, and description headings drawn from Why, What changed, Scope, Tradeoffs, Blast Radius, and Verification, in that order, with Scope always present.

## The todo list

The hook messages give these commands with the session filled in. Define `g` once as a shell function, never a variable holding the command, because zsh does not word-split a variable and every command then silently does nothing:

```
g() { python3 scripts/guard.py "$@" --session <agent:id>; }
g todo from <skill>
g todo add "<item>" ["<item>" ...]
g todo show <n>
g todo done <n> [<n> ...] --token <token> [--token <token> ...] [--note "..."]
g todo skip <n> [<n> ...] --reason "..."
g todo wait <n> [<n> ...] --reason "..."
g todo hold --until <HH:MM or ISO time> --reason "..."
g todo none --reason "..."
g todo list
g todo check
g todo clear --reason "..."
```

`todo check` exits 0 when no item is open or waiting, else 1 with the list, so it works as an autorun `--check`. `--not-run` on `todo done` is deprecated and ignored for one release; its `--reason` is kept as the note.

A subagent adds `--agent <its agent id>` after the session, from the message guard sends it, so its list is its own.

Never pipe guard output through a filter such as grep, because a refusal prints its reason there and the filter hides it.

`todo from` copies, with their order, the numbered items of a `## Steps` section, step headings (`## 1.`, `## Step 1,`, `## Phase A:`, `## Pass 1:`), or a numbered list right after the title. For a skill written another way, add its steps with `todo add`. Skip an item only for a reason the user would accept, because the reason is what they read. Clear the list only when the user stops the work. When every item resolves, list them with their marks in the final reply.

## The watchdog

```
python3 scripts/guard.py watch [--session <agent:id>]        # a background job of the lead's own
python3 scripts/guard.py watch --ack <pid> [--session <agent:id>]
python3 scripts/guard.py watch --stop [--session <agent:id>]
```

Time asks the lead a question; it never stops a job. Only a certain signal stops or blocks something: an event (a delegate handed back but its work still runs), a construct that cannot end (a self-matching `pgrep -f`, a poll loop on a verify run), or the lead's own decision.

The watchdog finds the agent process that started it (the first ancestor of its parent shell that is not a shell) and watches every other shell under it, each with the processes below it, as one job. It never looks at another agent's processes, and it exits with an error when it finds no agent process, because watching nothing is not silence. A job progresses when a file its processes write as stdout or stderr grows (found with lsof, or /proc on Linux, wherever the harness put it), when its processes use more CPU than `--cpu-floor` of one core between samples (so idle timers and pollers do not count), or when a process with a command line the job has not run before starts (so a poll loop that runs the same commands is silence). Without lsof or /proc it counts CPU time and new processes only, and says so once.

Each job's threshold adapts: once it has shown `--events` progress events (default 3), it is `--multiple` (default 3) times its own longest gap between them, and never less than `--initial` (default 300 s), which also holds until then. A wrong value costs one extra question, never a kill. The watchdog samples every `--interval` seconds (default 5) and sleeps in between, so it costs no tokens while every job progresses. When a job stays silent past its threshold, it prints one line per silent job (pid, what it runs, how long it is silent against its longest earlier gap, its last output line and output file) and exits 0, and the harness notifies the lead. The lead reads the job's output and processes, then stops a stuck job (its task-stop tool, or `verify.py stop <id>` for a verify script) or acknowledges an intentionally idle process with `watch --ack <pid>`, which the session's watchdogs never ask about again, and starts the watchdog again. A restarted watchdog learns each job's rhythm from scratch.

One watchdog runs per agent session: its pid file sits in the session's state with the watchdog's start time and session, and a second one refuses to start. A pid file is trusted, and `watch --stop` signals its pid, only while that pid runs a watchdog that started at the recorded time, so a pid reused by another process, another session's watchdog included, is never taken for it. It exits on its own when its agent process exits, so it never outlives the session; `watch --stop` ends it. When `ps` fails, which processes run is unknown, never "none": the watchdog refuses to start over a watchdog it cannot rule out, `watch --stop` signals nothing, and a running watchdog exits with an error after 3 failed samples in a row instead of watching blind.

## Usage limits and fallback

A usage limit never blocks delegate work: hand it to the next candidate instead of waiting. `python3 scripts/guard.py quota status` prints the registry. `python3 scripts/guard.py quota pick --role <planner|executor> [--avoid <agent[:model]> ...]` prints the first entry of that role in the orchestrator config (`<project>/.agents/orchestrator/models.json`, else `~/.agents/orchestrator/models.json`) whose agent is not limited and that no `--avoid` names, as `agent:model:effort`. It exits 1 when every candidate is limited, naming the earliest reset; then `todo hold` until that time. Only the lead's own limit, every candidate limited, or a check that tests one specific agent waiting for that agent's quota is a wait, and that wait is a hold, never a FAIL.

When the first pick breaks a separation rule, walk the fallback order, which `quota pick --relax` prints and follows:

1. a candidate that keeps every separation rule;
2. one that relaxes "reviewer from a different family";
3. one that relaxes "verifier on a different entry from the executor";
4. a candidate from the other role.

Pass the separation as `--avoid` (the executor's family for a reviewer, the executor's entry for a verifier); a relaxed pick prints which rule it relaxed. Report every relaxation in the PR's Verification section and in report.md.

## Lint

`python3 scripts/guard.py lint <skill name or SKILL.md path>`, or `--all` for every skill under the skill roots, reads a skill as `todo from` does. Errors (exit 1): no steps found in a skill that refers to its steps; an ordering phrase that names a step the skill does not have; a backticked gate whose script is not installed beside the skill; steps that wait on each other in a cycle. Warnings: a step that says "Close this step only when" without a backticked gate; a step both Mandatory and "Skip this step"; a step naming `../<x>/SKILL.md` for a skill not installed beside it. Lint a skill after editing its steps.

## Install and state

Guard has no hooks of its own. It runs inside the hook runtime of the `autorun` skill, which loads guard's rules whenever guard is installed beside it, so install autorun's hooks once (`python3 <autorun>/scripts/autorun.py install`) and keep both skills installed.

The usage-limit registry lives in `~/.agents/orchestrator/limits.json`. State lives in `~/.agents/guard/sessions/`, one file per agent session, with each subagent's list under its agent id in its session's file; sweeps that could not run are logged in `~/.agents/guard/errors.log`. Set `GUARD_SKILL_ROOTS` to a path list to override where guard looks for installed skills.

## Adding a rule

Write the rule in `scripts/guard_lib/rules.py` as a check on one hook event (`prompt`, `pre_tool`, `post_tool`, or `stop`) that returns `("deny", message)`, `("block", message)`, `("context", message)`, or `("pass", None)`, and add tests to `tests/test_guard.py` in this repo. Name the fix in the message, since the agent acts on it directly. Prefer a rule over another line of skill text whenever the convention can be checked from a hook payload.
